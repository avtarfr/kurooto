Phone calls, the call line and the phone app

Phone calls (modules/calls/, class Calls, id calls) let the user talk to Kurooto by voice and let Kurooto ring the user's phone. Three parties are involved:

  1. The daemon on the user's computer (modules/calls/*.py).
  2. The call line: a Cloudflare Worker plus one Durable Object (Line), deployed to the user's own free Cloudflare account from src/kurooto/data/worker/. It is reachable from the internet; the computer is not.
  3. The phone: the Android app (android/) or the installable web app (any browser, including iPhones, which only get notifications).

Audio never passes through the computer or the Worker: the Worker mints a short-lived Gemini Live token and the call page talks to Google directly.

The user's side of this is in ../user/calls.md and ../user/phone-app.md.

Secrets (Calls.SECRETS and deploy.ensure_secrets): calls.call_secret, calls.connector_secret, calls.ntfy_topic, calls.ntfy_key, calls.vapid_jwk, calls.vapid_public, calls.ntfy_token (optional, from kurooto ntfy-token: an ntfy account token, sent as Authorization: Bearer by Calls.publish_ntfy and the Worker's publish(), each retrying once without it on a 401/403; it moves ntfy's rate limits from the shared IP to the account; check_ntfy_token(server, token) asks GET /v1/account; Calls.set_ntfy_token keeps or clears it and redeploys the line in the background, from POST /api/phone/ntfy {token} (the Phone tab, the setup page's call box) and kurooto ntfy-token; GET /api/phone has ntfy_token and ntfy_limited. A 429 from ntfy emits calls_ntfy_limited; Calls.health is not OK while any came in the last 7 days and there's no token); also gemini.api_key (required) and calls.github_token (set by Notes sync, modules/notes_sync.py, so the line can read notes while the computer is off).

Deploying the line (modules/calls/deploy.py)

deploy(...) runs Deployer.run:

  1. prepare: Node via core/prereqs.py; copy FILES from data/worker into <app>/call-line (skip_built leaves out public/app.js and node_modules); copy the phone app (update/phone_app.py:current: the one downloaded from the running version's signed release, else data/kurooto.apk from an older package) to public/kurooto.apk, with public/kurooto-app.json ({"versionName"}, phone_app.TAG) beside it for the pairing page's label (pair.js; removed when there's no app), and remembers the app's sha256 (Deployer.apk); npm ci --ignore-scripts (skipped when the .kurooto-lock stamp matches the lockfile); esbuild bundles web/app.js.
  2. sign_in: wrangler login --browser=false, the URL opened in the user's browser. wrangler_env gives wrangler its own config home and strips CLOUDFLARE_*, CF_*, WRANGLER_* from the environment, so a developer's own Cloudflare login is never used or touched.
  3. subdomain: the account's workers.dev subdomain through the Cloudflare API (created as k-<hex> if missing).
  4. write_config / render_toml: fills wrangler.template.toml; the Worker name is kurooto-<hex> (new_name).
  5. ensure_secrets, wrangler deploy, wrangler secret bulk.
  6. Save calls.worker (with apk: the served app's sha256), then poll /health (24 times, 5 s apart).

deploy() runs one deploy at a time (_one; a second gets BUSY, deploying() tells).

Redeploys: fingerprint hashes the Worker source and the values baked into it (time zone, live_model, ntfy_server, notes_repo, whether a GitHub token exists, the ntfy token, hashed); needs_redeploy compares it with calls.worker.hash. Calls._line_update runs daily at 05:10 and redeploys unattended unless updates.mode is off.

A new phone app (0.5.21): Updates.phone_app (update/service.py, 2 min after a start and every 6 h) ends with _app_to_line: when deploy.app_behind(app) (a line exists, an app is here, and calls.worker.apk isn't its sha256; lines deployed before 0.5.21 have no apk, so they count as behind once), it books calls.app_line in APP_LINE_SOON_MIN (1) minute, key calls:app_line, not replacing one already booked. Calls._app_line does nothing once the line has the app; on a call (availability.on_call_until()) or while another deploy runs it books itself again in APP_LINE_BUSY_MIN (10); otherwise it deploys unattended in a thread (_spawn). Each try emits one calls_line_updated (why="phone_app", app, and on failure tries, error); a failure is retried in APP_LINE_RETRY_MIN (30) up to APP_LINE_TRIES (6), then the 05:10 update takes over. The second failure sends one message (why="calls.line_update"). Tests: tests/unit/test_apk_ship.py (the line fixture fakes deploy).

The connector (modules/calls/connector.py:Connector)

  • One outbound WebSocket to wss://<worker>/connect with header x-connector-secret; max_size 8 MB; the library's own pings off. Runs as Calls.background(stop), started by App.start_background.
  • Heartbeat: text "ping" every PING_S = 30 s; the Durable Object answers "pong" through setWebSocketAutoResponse without waking. Nothing heard for DEAD_S = 75 s ends the session and redials.
  • Reconnect back-off 2 s doubling to 60 s; failures go to app.presence.net_failed("line", e). Link state: <state>/calls/link.json.
  • Computer to Worker: hello (pull: true: hand over what waited one item at a time), state (Calls.state_message: setup, tools, brief, schedule, texts, voices, presence hours ...; pushed every STATE_S = 300 s or 1 s after poke()), index (the notes index, in parts, at most hourly), reply (answers to relayed requests), admin (operations).
  • Worker to computer: welcome (version, outbox: how many items wait, an away report; to a computer without pull, the whole queue as before), request (relayed HTTP), admin-reply, event, outbox (something was queued while the link looked away, or the queue isn't empty at a state push: take it).
  • _drainer (a session task): on outbox, asks admin("outbox", done={seq, status, note}) in a loop, handing each item to Calls.take_queued in a thread, until the answer has no item. The Worker drops an item only when the next ask names it done, so a crash mid-way repeats at most one item (answers and chat messages refuse a used nonce).
  • admin(...) / admin_wait(...) (from a thread; refuses on the event loop) / admin_later(...) (fire and forget; its True only means a socket existed).

Placing a call and ringing

  1. Calls.place(...) checks core/availability.py:Availability.call_block (on a call, quiet / held calls, focus, night, then module blockers such as classes and calendar events) unless alarm or force. A blocked call is booked for next_callable() and the user is told.
  2. Calls.schedule books it with scheduler.at(..., "calls.ring", key="calls:ring:<key>", grace_s=900) and pokes the connector so the line has the schedule too. Turned off, Calls.stop parks the booked calls:ring:* jobs in calls/parked-calls.json; start() books them again (_unpark), and one whose time passed is reported in a message, not rung late.
  3. Calls.ring:
  4. asks Calm first (core/calm.py:Calm.call_ok: by default one self-started call a day; the alarm and calls the user asked for are exempt). A refused call is held for the evening bundle as a line with a call link;
  5. records it in <state>/calls/rings.json;
  6. sends admin_later("ring", ...): the Worker's Line.ring mints a ticket (2 h; 3 h for alarms), publishes a k1-sealed message to ntfy for paired Android devices, and sends an empty Web Push (VAPID) to every subscribed browser, whose service worker (public/sw.js) then fetches /pending;
  7. publishes to ntfy directly from the computer (Calls.publish_ntfy) only when the line isn't connected, or its answer to ring (Calls._ring_fallback) doesn't say "android": true (an error, no answer, its publish failed, or no Android device paired): one ntfy message per ring;
  8. sends a Telegram notice with an Answer link (Calls.link, a t1 ticket in the URL fragment), or an urgent "the call line isn't connected" notice;
  9. schedules calls.missed at ring_s + 30 s, or ALARM_RING_S (300, the Worker's and the app's alarm ring)
  10. 30 s for an alarm.
  11. Calls._missed: stops the ring (stop-ring, or a direct ntfy stop when the line isn't connected), re-alerts at realert_min (not for alarms), and finally "Missed call" with Call back / In 30 min buttons; the owning module hears call_outcome(..., "missed").
  12. Calls._scheduled_ring skips a late or missed one-off when a line exists, assuming the line's cron placed it.

There is no FCM. Android rings through an ntfy JSON stream held by ListenService; browsers through Web Push.

When the computer is off, the Worker's cron (Line.tick, every minute) places scheduled calls itself (skipping ones more than 180 s late, holding non-alarm calls during a call), answers tools from the last brief, and queues tool calls, transcripts, events and answers until the computer takes them (Calls.take_queued, see the phone outbox below).

During a call

  • The call page (web/app.js, in CallActivity's WebView or a browser) POSTs /token; Line.token mints a single-use ephemeral Live token (30 min expiry, 2 min to start) and emits call_started (stops the ring; Calls.on_event marks the ring answered and writes <state>/calls/live.json).
  • The Live session is configured from Calls.config_template (system instruction with each tool's hint, the persona card and boundaries rule from core/persona.py, calls.persona through the same persona.clean, learned lessons, transcription, context compression) and Calls.texts. Its time line is It is %%NOW%%, their local time (<zone>), filled in by the Worker (TZ) or fallback.py; pending() starts with now too. Without the zone named, a Live model once planned in UTC ("1:30 PM" at 17:00 IST). Voice by kind: Calls.voice_for.
  • Tool calls: page to /tool, Worker to WebSocket, Calls.handle_request to Calls.run_tool. Tools are Calls.tools(): its own (pending_items, search_notes, read_note, schedule_call, call_now, hold_calls, run_task when Chat is on), app.ask.call_tools(), core/tools.py:sync_tools, and every enabled module's call_tools(). With the computer off, each tool's offline value decides: brief (answered from the last pushed brief), queue (done later), needs (the assistant says it can't).
  • /tasks is polled for finished jobs and approvals; Calls.on_call keeps availability.set_on_call 90 s ahead (ON_CALL_S), so nothing else rings and updates wait.
  • What needs attention: Calls.pending merges every enabled module's call_brief() with app.ask.call_brief() and core/assembler.py:call_brief() (open_threads, earlier: the last day's gists, within memory.budget_tokens). save_transcript also hands the user's lines to core/threads.py:from_call ("I'll send the draft tonight" opens a thread).
  • Module hooks the calls module looks for (hasattr in modules/calls/__init__.py): call_tools, call_brief, call_schedule, call_outcome, call_transcript, call_reschedule. Calls.agent_tools gives unattended AI runs only schedule_call and hold_calls.
  • Relayed HTTP paths handled by Calls.handle_request: /tool, /tasks, /answer, /chat, /transcript, /turn, /textcall, /upload (1 MB per part, 50 MB total, into the notes inbox folder from core/layout.py).

Fallback layers

modules/calls/fallback.py with data/worker/web/fallback.js (the page drives them):

  1. Live again: rotate() retries with BACKOFF_MS = [0, 1000, 3000], moving through calls.live_models; MID_CALL_RETRIES = 1 for a drop mid-call. live_profile adapts settings per model.
  2. Turn by turn: the phone's own speech recognition and TTS (speechKind: the Android bridge or Web Speech). Each turn goes to /turn, relayed to VoiceTurns.answer on the computer: a quick brain (Gemini text_model, or the local model with turn_brain = local), never an agent program, TURN_S = 25. With the computer off, the Worker's Line.textTurn uses Gemini directly with up to 4 tool rounds.
  3. Text on Telegram: /text-call to /textcall to TextCall.start; replies go through jobs (then="calls.textcall_said"), the conversation in <state>/calls/textcalls.json, ended after 20 min idle (TEXT_IDLE_S) or by the End button. While a text call is open, App.handle sends messages to it first (calls.textcall.takes(msg)).

Failures are counted in <state>/calls/live-health.json (LiveHealth.record) and reported by Calls.doctor_checks.

  • export default {fetch, scheduled} and the Durable Object Line (SQLite-backed, migration v1). Cron * * * * *.

The app's chat and the phone outbox (0.5.16)

The chat. modules/calls/chat.py:PhoneChat. A message typed in the app reaches PhoneChat.take, which builds Incoming(text, via="app", message_id="app:<id>", respond=...) and calls App.handle: commands, intents and Chat as on Telegram (core/turnon.py already offers its buttons for via app). respond and later answers go through PhoneChat.say, which keeps the buttons' data in <state>/calls/chat.json (last 100, 7 days) and sends admin_later("chat-say", msg=...); failed pushes are sent again from state_message (flush, last hour). Jobs answer with reply_to="app:<id>": core/notify.py:Notifier._deliver sends such a message to the chat channel only (and the desktop, by its kinds); with no chat channel it goes to Telegram without the reply_to. With notify.app_chat on, messages whose kind isn't in notify.app_kinds (and isn't call) also go to chat. A button press runs App.callback(data) and says its answer in the chat unless it's empty or "ok"; under the answer to a counting button (core/notify.py:counts, a "+1"; 0.5.20) the same button again, so the chat's notification can offer it too. Without Telegram (App.app_main(): Telegram off, Phone calls on; 0.5.18) the chat gets everything not in notify.app_kinds as if app_chat were on, Calm's Why? / Less of this rows included (core.md, Notify and Calm).

Files for the chat (0.5.18). PhoneChat.send hands a Message.file to send_file(path, caption, re_id), which makes the link in a thread (_file_now) and says it in the chat as a URL button:

  1. Drive upload on and ready: modules/google_drive.py:DriveUpload.put(path, temporary=True) (deleted after drive_upload.temp_days), button "Open in Drive".
  2. Else to_line(path): a fresh 32-byte key, line.seal_f1 (AES-256-GCM, raw nonce ‖ ciphertext+tag), sent with admin_wait("file-put", fid, part, parts, size, hours, data) in FILE_PART (384 KB) pieces, in order (fid, not id: id is the admin request's own). At most FILE_MAX (10 MB); kept FILE_HOURS (24). The link is <worker>/file#i=<fid>&k=<base64url key>&n=<name>; public/file.js fetches /sealed/<fid>, decrypts with WebCrypto, offers Save and shows text files. The Worker (Line.filePut, filesLive, fileGet) keeps parts under f:<id>:<n> and an index files ({parts, size, got, bytes, exp}), at most FILES_BYTES (30 MB) at once ({"error": "full", "note"} past it), and drops expired files on access and every cron tick.
  3. Else a plain message: the file stays on the computer, with its path and the dashboard's address.

modules/skills.py:send_file (kurooto send, the AI's send_file) goes to send_file directly when app_main(). Jobs._deliver sends a long answer's file with the text's reply_to, so an answer to the app's chat gets its file there too.

Files from the phone. Calls._upload records each saved file in <state>/calls/shared.json (PhoneChat.shared: name, path, note, time; last 20), and the filing job it submits with Chat on is Chat's own (Chat.own), so where it went joins the conversation. modules/chat.py:Chat.ask adds the last two hours' shares (SHARED_S) to a request that talks of a file (REFERS); record_turn keeps that note out of the history.

The web app's chat. public/talk.html / talk.js (at /talk): the documented API below with the device key from localStorage (kurootoDevice); its own copy of the chat in localStorage (kurootoChat); GET /chat?after= on opening, every 5 s while visible and on visibilitychange; a Kurooto chat push opens /talk (sw.js). The call page (paired browsers), the inbox and the pairing page link to it.

The phone outbox. The Worker's queue (one value: an index of items, each with a rising seq; a phone item's body under its own key q:<seq>) holds both the line's own items (tool, transcript, event) and phone items (answer, chat, upload, with device and oid). Past 200 items the oldest line items go, never phone items. A phone request is relayed only when the computer is online and no phone item is queued; otherwise it's queued, so order holds. Limits: OUTBOX_MAX 100 things (distinct oid), OUTBOX_BYTES 20 MB of files (checked for the whole file, parts × 512 KB, at part 0); over them, 507 with note. Only paired devices can queue; a ticket's upload while offline still gets 503. When the computer finishes an item (outbox op with done), the Worker drops it, records {oid, kind, ok, note, t} in odone (100, one day) and tells an Android sender by ntfy (below). Web devices aren't pushed for this (an iPhone must show something for every push); they poll /outbox or /chat.

Sealing. Android: the fields are k1-sealed with the ntfy key (as answers are), so ntfy can't read them; the Worker holds that key (NTFY_KEY) and stores the sealed form. Web: plain JSON over HTTPS with the device key. Either way ts + n (16-64 hex) make it single use (PhoneApp._spend_nonce, 10-minute freshness against the Worker's at). Shared files are stored as sent (base64) while they wait.

API for phone apps

All with header x-call-secret: d1.<id>.<secret> (a paired device). Ids are 16 lowercase hex.

RouteBody / queryAnswer
POST /chat (Android){"id", "k1": seal_k1(ntfy key, JSON fields)}see below
POST /chat (web){"id", "ts", "n", "text", "to"?} or {"id", "ts", "n", "button": <number>, "msg": <Kurooto message id>}see below
GET /chat?after=<seq>{"seq", "msgs": [message...] with seq > after, "waiting", "done", "computer", "assistant"}
GET /outbox{"waiting": [{"oid", "kind", "at"}], "done": [{"oid", "kind", "ok", "note", "t"}], "computer": "online"\|"offline"}
GET /pendingas before, plus "chat": the last 5 messages from Kurooto (for the service worker)
POST /answeras beforeas before; offline and queued: {"ok": true, "queued": true, "note"}
POST /upload?name&note&id&part&partsraw bytes, at most 512 KB a partonline: the computer's answer; offline (device key, id given): {"ok": true, "queued": true, "part", "note"}

The sealed fields (Android) are the web body's fields plus "id" (must match the outer id): {"id", "ts", "n", "text", "to"?} or {"id", "ts", "n", "button", "msg"}. text is at most 4000 characters (16 000 bytes of body).

POST /chat answers: computer online, 200 {"ok": true, "id", "said": [message...]} (the immediate replies; later ones arrive as chat messages), or a button's 200 {"ok": true, "note"}; offline, 200 {"ok": true, "queued": true, "note"}; 400 {"ok": false, "note"} (empty, no id, can't be opened: pair again); 409 {"ok": false, "note"} (stale or used nonce); 507 {"error": "full", "note"} (the outbox is full); 401 (not paired).

A chat message: {"id", "seq", "from": "you"|"kurooto", "text" (at most 6000), "at" (seconds), "buttons": [{"label"} | {"label", "url"}] (at most 6; a button with url opens it, one without is pressed by its index), "reply" (true: a reply to it, with to, reaches the feature that sent it), "re"? (the message it answers), "title"?}. Your own message appears in the log (from: "you") once the computer took it. The line keeps the last 50, each 3 days.

What an app should do: keep its own copy of the chat; generate the id; show "Waiting for your computer" for anything answered queued, until GET /outbox (or /chat) no longer lists its oid (the chat message's id, the answer's item id, the upload's id); catch up with GET /chat?after=<last seq> on opening and after a push.

Pushes. Each Kurooto message: Android gets a k1 ntfy message {"title", "message", "tags": ["stop", "chat"], "id", "seq", "re", "reply", "buttons", "time", "assistant"} (text trimmed to fit ntfy; the app fetches /chat for the rest); web devices get an empty Web Push and find it in /pending's chat. When a queued item from an Android phone went through: {"tags": ["stop", "outbox"], "dev": <device id>, "done": [{"oid", "kind", "ok", "note"}]}. stop makes apps older than 0.5.16 ignore both.

Admin ops. chat-say {msg, assistant}: store a message (from you or kurooto; once per id) and push it if it's Kurooto's; answers {ok, seq, android, web}. outbox {done?}: drop done.seq and tell its phone; answer the next item {"item": {seq, kind, at, ..., body | body_b64}, "left"} or {"item": null}.

Today and the phone's own alarm (0.6.0)

The list. modules/calls/today.py:PhoneToday.snapshot() builds it from core/actions.py:today (the dashboard's Today API) plus the deadlines' parts and kinds and core/threads.py:open_threads: {"v": 1, "date", "day", "classes": [{"time", "name", "skipping"}], "events": [line], "due": [{"id", "title", "due", "when", "parts"?, "done"?, "acts": ["done", "+1"?] | "exam": true}], "reminders": [{"when", "what"}], "alarm": {"next", "daily", "at": [s...] (every alarm still to ring: Alarm.upcoming()), "snooze_min", "reason"} | {}, "threads": [{"text"}], "questions": n}. No relative times ("in 3 hours"), so an unchanged day is byte-for-byte the same; cut to TODAY_MAX (40 000 bytes) by dropping the longest list's last rows.

Handing it over. Connector.push_state calls PhoneToday.push(connector) after each state push (every 5 minutes, and on poke()). It asks the line for its devices, seals the list (plus "made") for each Android device with a seal key (line.seal_s1, as Reminders with the lid shut does) and sends today-put {rev, seal: {device id: s1 token}, changed} when the digest of list + keys changed, poke() was called, or the last hand-over is REFRESH_S (15 minutes) old. changed (the list itself changed) makes the Worker nudge Android phones. Events in CHANGES (deadline, alarm, reminder, thread events, action, button_tapped) call poke() through core/events.py:subscribe (registered in Calls.start), and so does the line's device_key event. calls.today = false: one today-put {seal: {}, off: true} and nothing more. An older line answers unknown op and is left alone until it's redeployed.

The Worker. today-put: a lower rev than the stored one is refused (stale); each token (TODAY_TOKEN, an s1 of at most 110 000 characters, for an Android device) is stored under today:<device id>, devices no longer listed lose theirs, the index today keeps {rev, devs, at (ISO), off}; changed or off publishes {"tags": ["stop", "today"]} to ntfy (stop: older apps ignore it). revoke deletes the device's copy. GET /today (a paired device): {"today": this device's token | null, "at": when it came | null, "off", "computer": "online" | "offline"}.

Taps. The app sends Done / +1 as a chat message {"id", "ts", "n", "today": {"id": <deadline id>, "do": "done" | "+1"}} (k1-sealed, through /chat, so it waits in the phone outbox like any chat message); PhoneChat.take passes today to PhoneToday.act, which checks the action and the id (open, not a quiz or exam) and runs App.callback("dl:<id>:<do>"), the deadline Telegram message's own button. Nothing is said in the chat; the note comes back in the answer (200 {"ok", "note"}, 400 bad or not tappable, 410 gone or not open).

The app. Today.fetch (on opening, on the today nudge, when the ntfy stream reconnects more than 5 minutes after the last fetch) opens the token with Seal, keeps it in today.json and hands alarm to Alarms.update. TodayView draws it on MainActivity's first screen under Call and Chat (its own column; it re-draws when a fetch lands), with Done / +1 under a tapped deadline (Chat.today, waiting kind today).

The alarm on the phone. Alarms.schedule sets the next of the computer's times and a snooze tapped here (AlarmPlan.next, which leaves out the one that last rang here and anything within SAME_S, 5 minutes, of it) with AlarmManager.setAlarmClock (shown in the status bar, exempt from Doze), or setAndAllowWhileIdle when Android 12+ refuses exact alarms (SCHEDULE_EXACT_ALARM on 12, maxSdkVersion 32; USE_EXACT_ALARM from 13). It's set again after every change, after it rings, and on boot (BootReceiver). Firing: ActionReceiver.ALARM → Alarms.fired → ListenService.localAlarm (the running service, or a start with ACTION_ALARM; if Android won't start it, the ringing notification alone) → ringLocal: rings as the wake-up call with since local:<s>, Stop and Snooze, on CallActivity's ringing screen (local extra, no call link). One alarm, not two:

  • the call for an alarm arriving while local: rings joins it (ListenService.ring): no second sound, the notification becomes the call's, and a showing CallActivity gets the call's intent (Answer appears);
  • the phone's alarm doesn't ring when an alarm call within SAME_S rang already (Alarms.callRang/lastCall);
  • Stop or Snooze (local or the call's) is recorded (Alarms.replied: alarmDone = "<s>:decline|later:<when>"); a call for the same alarm arriving within HANDLED_KEEP_S (30 minutes) is answered that way at once with /ring-reply, without ringing (AlarmPlan.answered). Snooze also sets the phone's own snooze (alarm.snooze_min from the list), so it rings again with nothing else reachable.

The app never adds an alarm of its own beyond that snooze: what it rings is the computer's list, which only has the alarms core/tap.py lets through.

Notification buttons. Buttons.pick (plain Java, TodayTest) chooses a message's quick buttons by label: counting (+<n>), Done, then snoozes (Snooze..., +<n> min|h), at most 3; Buttons.addDone when it snoozes but has no Done. Inbox.show uses them for kinds reminder and deadline (Reply moves to the answer window when there's no room; the app's own Done answers {"dismiss": true}, which PhoneApp.answer already takes: off every phone); ListenService.chatNote for any chat message (its own Done just cancels the notification). A sealed reminder (ListenService.sealedNote) gets Done and +10 min / +1 h, kept on the phone (ActionReceiver.SEALED_SNOOZE shows it again with an inexact alarm): the computer is asleep when those come.

Tell Kurooto, the iPhone Shortcut (0.6.0)

Apple doesn't allow generating a Shortcut file, so the phone shows a recipe with a link to paste.

  • The link. <line>/tell/tk1.<8 hex id>.<32 hex secret>, made by the Worker for a paired device: POST /shortcut/new (device key; any older link of that device is dropped, so one per device) answers {ok, id, token, url}; GET /shortcut says whether the device has one ({shortcut: {id, created, used} | null}); POST /shortcut/off drops it. Stored in the Durable Object under tells: {<id>: {hash: sha256(secret), device, created, used}}. Making one emits the event shortcut_made (Calls.on_event notifies, Calm reason calls.shortcut_made, exempt "security").
  • Scope. Line.fetch routes /tell/tk1. before auth(), which never accepts a tk1 token, so the link opens no other route (401 everywhere else). Line.tellSend takes {"text"} as JSON, a form or plain text (at most TELL_TEXT, 4000), checks the hash and that its device is still paired, sets used, and builds the body the web app's chat would ({device, at, id, ts, n, text, via: "shortcut"}: no button, no to): relayed to /chat (so PhoneChat.take handles it like any phone message, nonce and all) or queued in the phone outbox as chat. The answer is text/plain for the Shortcut to speak: the immediate said texts joined, or the queued note, or the refusal (401 revoked/wrong, 400 empty, 405 not POST, 413, 507).
  • The computer's side. Calls.shortcuts() (admin_wait("tells"); [] from an older line) and Calls.shortcut_revoke(id) (tell-revoke, tid); GET /api/phone has shortcuts, POST /api/phone/shortcut/revoke {id}; the Phone tab lists them with Revoke. revoke (unpairing) drops the device's link; Line.fresh (after kurooto rotate) deletes tells with the devices.
  • The pages. public/shortcut.js renders the recipe into #shortcut (on settings.html, and on pair.html once an iPhone in standalone mode has paired: data-auto makes a link if the device has none). The link is kept in localStorage (kurootoTell) only; if the line's id differs (revoked or remade elsewhere), the page drops it and offers a new one. public/qr.js (KurootoQR.svg(text)): byte mode, level M, versions 1-20, drawn on the phone so the link never leaves it; tests/unit/test_shortcut.py compares it module by module with segno (segno pads a byte-aligned stream with a zero byte where the standard has 0xEC, so the test uses data that fills each version).

Pairing

  1. Calls.pair_start: line.pair_code() (8 characters from CODE_ALPHABET) sent with admin_wait("pair-code", minutes=15); the Worker keeps only its SHA-256 hash. The link <worker>/pair#c=CODE is shown as a QR (segno). Commands /phone, /phones, /unpair; dashboard POST /api/phone/pair, phone/revoke, phone/test.
  2. The phone opens the link. public/pair.js either hands it to the Android app (kurooto://pair / intent:// to PairActivity) or pairs the browser itself.
  3. Line.claim (single-use code, 30 failures an hour, at most 10 devices) returns a device key d1.<8 hex>.<64 hex> (the Worker stores only its hash), names, the ntfy topic and key (Android only) and the VAPID public key.
  4. Browsers subscribe to Web Push (/push/subscribe); Android sends its P-256 public key to /device/key for sealed (s1) data.

kurooto rotate (cli.py to core/leave.py:rotate_command, rotate_line): deletes the line keys (LINE_KEYS), makes new ones (deploy.ensure_secrets) and redeploys, restoring the old keys if that fails. The Worker's Line.fresh notices the new call secret and forgets devices, tickets and pair codes, so every phone pairs again. The Gemini key is not rotated.

Crypto, and the shared vectors

All three implementations must agree byte for byte: Python modules/calls/line.py, the Worker (sealK1, openK1, signedTicketOk in worker.js), Java (android/src/.../Crypto.java, Seal.java).

NameFormat
k1AES-256-GCM, 12-byte nonce: "k1." + base64url(nonce ‖ ciphertext+tag)
f1a file for the chat: raw bytes nonce ‖ ciphertext+tag (AES-256-GCM, a fresh key per file, base64url in the link's fragment; Python line.seal_f1/open_f1, browser public/file.js; no Java side)
t1t1.<expiry ms>.<hex HMAC-SHA256 with the call secret>
d1device keys d1.<id>.<secret>
s1ECDH P-256, HKDF-SHA256 (salt: the ephemeral public key, info "kurooto s1") to an AES key, then k1

tests/fixtures/call-vectors.json holds k1, t1 and s1 vectors, checked by tests/unit/test_calls.py (test_k1_and_t1_match_the_shared_vectors, and test_the_worker_agrees_with_the_vectors running tests/js/vectors.mjs in Node), android/test/CryptoTest.java (k1, s1; CI job android), and tests/unit/test_lidsafe.py (s1). Changing any format means changing all three and the vectors in one commit.

Known problems and doc mismatches

  • A shared file's part that the computer took but didn't confirm (it crashed in between) is written twice when the outbox is taken again; chat messages and answers are protected by their nonce, file parts aren't.
  • With no Android device paired, the computer still publishes each ring to ntfy once (the Worker's answer can't tell "no Android device" from "its publish failed").
  • A sealed file's link holds its key, and the link is part of a chat message the call line keeps (3 days): the file is only as private from the call line as the chat is.
  • The phone's own alarm and its call are matched by time (AlarmPlan.SAME_S, 5 minutes): alarms set less than 5 minutes apart ring on the phone as one. A sealed reminder snoozed on the phone isn't known to the computer.
  • Today and the phone's alarm are untested on a real phone as of 0.6.0's build (JVM tests, the debug build, lint and the Worker tests only).
  • calls.ring_s is never sent to the Worker or the app, which ring 60 s (5 minutes for an alarm) whatever it says.
  • Turn-by-turn calls run tools through core/tools.py:run_tool and don't reach Calls.tool_log; a call page from before 0.5.8 (until the Worker is deployed again) sends no since, so its tools share the "" log.
