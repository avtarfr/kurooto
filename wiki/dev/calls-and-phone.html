Phone calls, the call line and the phone app

Phone calls (modules/calls/, class Calls, id calls) let the user talk to Kurooto by voice and let Kurooto ring the user's phone. Three parties are involved:

  1. The daemon on the user's computer (modules/calls/*.py).
  2. The call line: a Cloudflare Worker plus one Durable Object (Line), deployed to the user's own free Cloudflare account from src/kurooto/data/worker/. It is reachable from the internet; the computer is not.
  3. The phone: the Android app (android/) or the installable web app (any browser, including iPhones, which only get notifications).

Audio never passes through the computer or the Worker: the Worker mints a short-lived Gemini Live token and the call page talks to Google directly.

The user's side of this is in ../user/calls.md and ../user/phone-app.md.

Deploying the line (modules/calls/deploy.py)

deploy(...) runs Deployer.run:

  1. prepare: Node via core/prereqs.py; copy FILES from data/worker into <app>/call-line (skip_built leaves out public/app.js and node_modules); copy the phone app (update/phone_app.py:current: the one downloaded from the running version's signed release, else data/kurooto.apk from an older package) to public/kurooto.apk, with public/kurooto-app.json ({"versionName"}, phone_app.TAG) beside it for the pairing page's label (pair.js; removed when there's no app), and remembers the app's sha256 (Deployer.apk); npm ci --ignore-scripts (skipped when the .kurooto-lock stamp matches the lockfile); esbuild bundles web/app.js.
  2. sign_in: wrangler login --browser=false, the URL opened in the user's browser. wrangler_env gives wrangler its own config home and strips CLOUDFLARE_*, CF_*, WRANGLER_* from the environment, so a developer's own Cloudflare login is never used or touched.
  3. subdomain: the account's workers.dev subdomain through the Cloudflare API (created as k-<hex> if missing).
  4. write_config / render_toml: fills wrangler.template.toml; the Worker name is kurooto-<hex> (new_name).
  5. ensure_secrets, wrangler deploy, wrangler secret bulk.
  6. Save calls.worker (with apk: the served app's sha256), then poll /health (24 times, 5 s apart).

deploy() runs one deploy at a time (_one; a second gets BUSY, deploying() tells).

Redeploys: fingerprint hashes the Worker source and the values baked into it (time zone, live_model, ntfy_server, notes_repo, whether a GitHub token exists, the ntfy token, hashed); needs_redeploy compares it with calls.worker.hash. Calls._line_update runs daily at 05:10 and redeploys unattended unless updates.mode is off.

A new phone app (0.5.21): Updates.phone_app (update/service.py, 2 min after a start and every 6 h) ends with _app_to_line: when deploy.app_behind(app) (a line exists, an app is here, and calls.worker.apk isn't its sha256; lines deployed before 0.5.21 have no apk, so they count as behind once), it books calls.app_line in APP_LINE_SOON_MIN (1) minute, key calls:app_line, not replacing one already booked. Calls._app_line does nothing once the line has the app; on a call (availability.on_call_until()) or while another deploy runs it books itself again in APP_LINE_BUSY_MIN (10); otherwise it deploys unattended in a thread (_spawn). Each try emits one calls_line_updated (why="phone_app", app, and on failure tries, error); a failure is retried in APP_LINE_RETRY_MIN (30) up to APP_LINE_TRIES (6), then the 05:10 update takes over. The second failure sends one message (why="calls.line_update"). Tests: tests/unit/test_apk_ship.py (the line fixture fakes deploy).

The connector (modules/calls/connector.py:Connector)

  • One outbound WebSocket to wss://<worker>/connect with header x-connector-secret; max_size 8 MB; the library's own pings off. Runs as Calls.background(stop), started by App.start_background.
  • Heartbeat: text "ping" every PING_S = 30 s; the Durable Object answers "pong" through setWebSocketAutoResponse without waking. Nothing heard for DEAD_S = 75 s ends the session and redials.
  • Reconnect back-off 2 s doubling to 60 s; failures go to app.presence.net_failed("line", e). Link state: <state>/calls/link.json.
  • Computer to Worker: hello (pull: true: hand over what waited one item at a time), state (Calls.state_message: setup, tools, brief, schedule, texts, voices, presence hours ...; pushed every STATE_S = 300 s or 1 s after poke()), index (the notes index, in parts, at most hourly), reply (answers to relayed requests), admin (operations).
  • Worker to computer: welcome (version, outbox: how many items wait, an away report; to a computer without pull, the whole queue as before), request (relayed HTTP), admin-reply, event, outbox (something was queued while the link looked away, or the queue isn't empty at a state push: take it).
  • _drainer (a session task): on outbox, asks admin("outbox", done={seq, status, note}) in a loop, handing each item to Calls.take_queued in a thread, until the answer has no item. The Worker drops an item only when the next ask names it done, so a crash mid-way repeats at most one item (answers and chat messages refuse a used nonce).
  • admin(...) / admin_wait(...) (from a thread; refuses on the event loop) / admin_later(...) (fire and forget; its True only means a socket existed).

Placing a call and ringing

  1. Calls.place(...) checks core/availability.py:Availability.call_block (on a call, quiet / held calls, focus, night, then module blockers such as classes and calendar events) unless alarm or force. A blocked call is booked for next_callable() and the user is told.
  2. Calls.schedule books it with scheduler.at(..., "calls.ring", key="calls:ring:<key>", grace_s=900) and pokes the connector so the line has the schedule too. Turned off, Calls.stop parks the booked calls:ring:* jobs in calls/parked-calls.json; start() books them again (_unpark), and one whose time passed is reported in a message, not rung late.
  3. Calls.ring:
  4. asks Calm first (core/calm.py:Calm.call_ok: by default one self-started call a day; the alarm and calls the user asked for are exempt). A refused call is held for the evening bundle as a line with a call link;
  5. records it in <state>/calls/rings.json;
  6. sends admin_later("ring", ...): the Worker's Line.ring mints a ticket (2 h; 3 h for alarms), sends a k1-sealed message to paired Android devices (Line.toPhones: their own connections first, and ntfy as a second path for rings, below), and an empty Web Push (VAPID) to every subscribed browser, whose service worker (public/sw.js) then fetches /pending;
  7. when the line's WebSocket isn't connected, hands the ring to the line over HTTPS instead (Calls.send_phones: POST <line>/send, below) and publishes to ntfy from the computer (Calls.publish_ntfy) only when that fails (unreachable, an older line) or the line had no way to an Android phone; when connected, publishes only when its answer to ring (Calls._ring_fallback) doesn't say "android": true (an error, no answer, neither path worked) and doesn't say "phones": 0 (a 0.7.0 line with no Android phone paired: nothing to ring). One ring, not two;
  8. sends a Telegram notice with an Answer link (Calls.link, a t1 ticket in the URL fragment), or an urgent "the call line isn't connected" notice;
  9. schedules calls.missed at ring_s + 30 s, or ALARM_RING_S (300, the Worker's and the app's alarm ring)
  10. 30 s for an alarm.
  11. Calls._missed: stops the ring (stop-ring, or send_phones when the line isn't connected), re-alerts at realert_min (not for alarms), and finally "Missed call" with Call back / In 30 min buttons; the owning module hears call_outcome(..., "missed").
  12. Calls._scheduled_ring skips a late or missed one-off when a line exists, assuming the line's cron placed it.

There is no FCM. Android rings through its own WebSocket to the line (0.7.0, Direct) and an ntfy JSON stream as the fallback, both held by ListenService; browsers through Web Push.

The Android app's own connection (0.7.0)

Why: ntfy.sh limits each internet address (a free account too: GET /v1/account says basis: ip, 250 messages a day), and a campus shares one address, so rings were refused with 429 and phones stayed silent. Now the line delivers to the app directly and ntfy is the fallback.

Transport: a WebSocket to the Durable Object, hibernatable. Chosen over Server-Sent Events or long polling because only a hibernated WebSocket costs nothing while idle: an SSE stream or a held long-poll keeps the Durable Object awake (billed duration the whole time; one phone all day would be ~10 800 GB-s of the free plan's 13 000), while a socket accepted with state.acceptWebSocket lets it sleep, and the text "ping" is answered "pong" by setWebSocketAutoResponse without waking it. Android 6 has no WebSocket client and the app uses no libraries, so android/src/.../WebSock.java is a small RFC 6455 client over java.net sockets (TLS from HttpsURLConnection.getDefaultSSLSocketFactory(), so Tls's ISRG Root X1 applies on Android < 7.1.1, and the host name checked with HttpsURLConnection.getDefaultHostnameVerifier()); text messages, fragments, ping/pong, close, masked client frames, a 1 MB cap; a read timeout only between messages (one that stalls mid-message breaks the stream).

The Worker (worker.js):

  • GET /phone?after=<seq> (an upgrade, header x-call-secret: d1...; Android devices only: 403 for web, 401 unpaired, 426 without an upgrade). Line.phoneConnect closes the device's older socket (one per device), accepts with tags ["phone", "dev:<id>"] and attachment {kind: "phone", dev, at}, sends {"type": "hello", seq, version}, then replays from the phone log: every item with seq > after if 0 < after <= log.seq, else the last PHONE_NEW_MS (10 min). Then each message as {seq, k1}; the k1 is the same sealed JSON ntfy gets, plus mid (16 hex).
  • Sockets are told apart by attachment: Line.computers() (no kind: "phone"; a socket from before 0.7.0 counts as the computer's) is what online, lastSeen, tell, relay and connect (which replaces only the computer's) use; webSocketMessage from a phone only refreshes its at and is otherwise ignored (a phone can't send admin or anything else to the computer's handler); webSocketClose/Error of a phone doesn't touch seen.
  • Line.phonesHeard(): {device id: ms} from each phone socket's auto-response timestamp or at. Connected = heard within PHONE_FRESH_MS (6 min).
  • Line.toPhones(fields, assistant) (rings, stops, inbox messages, clears, chat, outbox done, Today nudges, sealed reminders): no Android device paired, nothing; else seal once with mid, append to the phone log (plog: {seq, items: [{seq, t, k1}]}, last PHONE_LOG_MAX 60, PHONE_LOG_MS 6 h), send down every phone socket, and publish() to ntfy when it's a ring (tag call) or some paired Android device isn't connected. Returns true when a connected phone has it or ntfy took it. publish(env, k1, priority) now takes the sealed message.
  • POST /send (no device key; x-connector-secret): {fields, assistant} (at most SEND_MAX 8000 bytes) through toPhones; answers {ok, android, phones} (phones: Android devices paired). ring answers carry phones too.
  • devices (admin) gives Android devices connected and heard (ISO or null); revoke closes the device's socket (code 1008).

The computer (modules/calls/__init__.py): Calls.send_phones(fields) is what used to be a direct publish_ntfy (the ring and its stop while the line's WebSocket is down): _via_line POSTs /send (10 s, through core/egress.py as the line's own host); None (unreachable, 401/404 from a line before 0.7.0, not ok) or android: false with phones > 0 falls back to publish_ntfy with the existing token logic; phones: 0 publishes nothing. Calls.devices() keeps the list for phones_direct(); the Phone tab shows connected per Android phone.

The app (android/): ListenService runs Direct (Direct.java) beside the ntfy stream; both hand opened messages to ListenService.deliver, which drops a mid seen before (Prefs.firstTime, LinkRules.seen: the last SEEN_MAX 200 ids in prefs seenIds; a message without mid, from an older line, is never a copy), so a ring arriving both ways rings once and a replayed message isn't shown twice. Direct:

  • connects to LinkRules.target(Prefs.url, Prefs.directSeq); after each {seq, k1} stores directSeq; a hello with a lower seq than stored (the log started again: a new line, a rotate) lowers it;
  • pings with "ping" when PING_MS (60 s, elapsedRealtime, so time asleep counts) has passed, checked on every read timeout (READ_MS 20 s), after every message, on every line of the ntfy stream (ntfy's own ~45 s keepalive wakes the phone anyway) and from an inexact setAndAllowWhileIdle wake-up alarm every KEEP_MS (4 min; Doze spaces these to about one per 9-15 min; ActionReceiver.KEEPALIVE, goAsync, re-armed each time, which also restarts the service if Android stopped it); a ping unanswered for DEAD_MS (30 s) closes the socket;
  • reconnects after LinkRules.backoffMs (2 s doubling to 60 s, plus up to a third at random); 404, 401, 403 or 426 (a line before 0.7.0, or unpaired) waits OLD_MS (30 min) and ntfy carries everything meanwhile;
  • on each connection sends the seal key and fetches Today if it's 5 minutes old, as the ntfy loop does.

MainActivity's This phone card says whether it's connected now (ListenService.direct()).

Mixed versions. Old app + new line: no socket, so the device is never connected and everything also goes to ntfy, as before (the extra mid field is ignored). New app + old line: /phone is 404, the app keeps to ntfy and asks again every 30 minutes. New computer + old line: /send is 401, so publish_ntfy as before; no phones in ring answers, so _ring_fallback behaves as before. The line itself is redeployed by the existing paths: the new phone app fetched after an update (Updates.phone_app → app_behind → calls.app_line within minutes), else the 05:10 _line_update (needs_redeploy: the Worker source is in fingerprint). A deploy disconnects every WebSocket; the computer and the phones reconnect by themselves, and the phones get what was sent meanwhile from the log.

Cloudflare's free plan (Workers Free; Durable Objects on it are SQLite-backed only), from Cloudflare's pricing and limits pages as of 2026-10: 100 000 Worker requests a day; for Durable Objects 100 000 requests a day, 13 000 GB-s of duration a day, 5 million rows read and 100 000 rows written a day, 5 GB stored; limits reset at 00:00 UTC, and past one, operations of that kind fail. WebSockets: opening one is a request; incoming messages are billed 20 to 1 as requests; outgoing messages and incoming protocol pings are free; a hibernated object isn't billed for duration (it hibernates after about 10 s with nothing to do), and auto-responses don't wake it or add duration (the docs don't say whether they count as requests; counted below as incoming messages). Up to 32 768 hibernatable sockets per object, 10 tags each, 32 MiB a message. One phone connected all day: at most 1 440 pings a day (one a minute; far fewer asleep) = at most 72 billed requests, plus one Worker request and one Durable Object request per reconnect (even 300 reconnects on a bad network is 600), no extra duration while idle, and one row read and one written per message to the phones (a few hundred a day). Ten phones (MAX_DEVICES) would still be well under 5% of the request limits. For comparison, what the line already uses: the cron wakes the object every minute (1 440 requests, roughly 1 440 × 10 s × 128 MB ≈ 1 850 GB-s a day), and the computer's connector pings every 30 s (at most 144 billed requests).

When the computer is off, the Worker's cron (Line.tick, every minute) places scheduled calls itself (skipping ones more than 180 s late, holding non-alarm calls during a call), answers tools from the last brief, and queues tool calls, transcripts, events and answers until the computer takes them (Calls.take_queued, see the phone outbox below).

During a call

  • The call page (web/app.js, in CallActivity's WebView or a browser) POSTs /token; Line.token mints a single-use ephemeral Live token (30 min expiry, 2 min to start) and emits call_started (stops the ring; Calls.on_event marks the ring answered and writes <state>/calls/live.json).
  • The Live session is configured from Calls.config_template (system instruction with each tool's hint, the persona card and boundaries rule from core/persona.py, calls.persona through the same persona.clean, learned lessons, transcription, context compression) and Calls.texts. Its time line is It is %%NOW%%, their local time (<zone>), filled in by the Worker (TZ) or fallback.py; pending() starts with now too. Without the zone named, a Live model once planned in UTC ("1:30 PM" at 17:00 IST). Voice by kind: Calls.voice_for.
  • Tool calls: page to /tool, Worker to WebSocket, Calls.handle_request to Calls.run_tool. Tools are Calls.tools(): its own (pending_items, search_notes, read_note, schedule_call, call_now, hold_calls, run_task when Chat is on), app.ask.call_tools(), core/tools.py:sync_tools, and every enabled module's call_tools(). With the computer off, each tool's offline value decides: brief (answered from the last pushed brief), queue (done later), needs (the assistant says it can't).
  • /tasks is polled for finished jobs and approvals; Calls.on_call keeps availability.set_on_call 90 s ahead (ON_CALL_S), so nothing else rings and updates wait.
  • What needs attention: Calls.pending merges every enabled module's call_brief() with app.ask.call_brief() and core/assembler.py:call_brief() (open_threads, earlier: the last day's gists, within memory.budget_tokens). save_transcript also hands the user's lines to core/threads.py:from_call ("I'll send the draft tonight" opens a thread).
  • Module hooks the calls module looks for (hasattr in modules/calls/__init__.py): call_tools, call_brief, call_schedule, call_outcome, call_transcript, call_reschedule. Calls.agent_tools gives unattended AI runs only schedule_call and hold_calls.

Known problems and doc mismatches

  • A shared file's part that the computer took but didn't confirm (it crashed in between) is written twice when the outbox is taken again; chat messages and answers are protected by their nonce, file parts aren't.
  • With no Android device paired and a line from before 0.7.0, the computer still publishes each ring to ntfy once (that line's answer can't tell "no Android device" from "its publish failed"; a 0.7.0 line says phones).
  • The app's own connection is untested on a real phone as of 0.7.0's build (JVM tests against a local server, the debug build, lint and the Worker tests): how often Doze lets the keepalive alarm and the socket through on each maker's phone, and whether a carrier or campus NAT drops a socket idle for 4+ minutes, are unknown. A dropped socket that still looks connected to the line (heard within 6 min) means a non-ring message waits until the phone's next ping fails and it reconnects (the replay brings it; rings always also go through ntfy).
  • Line.toPhones writes the phone log on every message even when no phone ever connects (an app before 0.7.0): one row write each, well inside the free plan.
  • A sealed file's link holds its key, and the link is part of a chat message the call line keeps (3 days): the file is only as private from the call line as the chat is.
  • The phone's own alarm and its call are matched by time (AlarmPlan.SAME_S, 5 minutes): alarms set less than 5 minutes apart ring on the phone as one. A sealed reminder snoozed on the phone isn't known to the computer.
  • Today and the phone's alarm are untested on a real phone as of 0.6.0's build (JVM tests, the debug build, lint and the Worker tests only).
  • Systems and the Notes map (0.7.0) were checked on one real phone only with a stored sample copy (the WebView, its assets, the colours, a tap); fetching from a real call line and watching ran against wrangler dev only. The notes map's layout is worked out on the phone each time (no positions are kept), so it differs a little from the dashboard's and takes a few seconds to settle.
  • calls.ring_s is never sent to the Worker or the app, which ring 60 s (5 minutes for an alarm) whatever it says.
  • Turn-by-turn calls run tools through core/tools.py:run_tool and don't reach Calls.tool_log; a call page from before 0.5.8 (until the Worker is deployed again) sends no since, so its tools share the "" log.
  • Never draw R.mipmap.ic_launcher with Compose's painterResource. From API 26 that id resolves to the adaptive icon XML (mipmap-anydpi-v26/ic_launcher.xml), which painterResource rejects ("Only VectorDrawables and rasterized asset types are supported"). 0.7.0 did this for the mark at the top of Today and crashed on launch on every phone from Android 8; 0.7.1 draws R.drawable.k_mark (a PNG in drawable-nodpi) instead. Lint and build.sh --test don't catch it: open a --dev build on a real phone (--ez demo true reaches Today unpaired) before every release that touches the app.
