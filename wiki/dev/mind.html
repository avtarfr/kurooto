Brain (the mind), for developers

Brain is Kurooto's mind (0.8.0), built in stages from the spec in the maintainer's build folder (17 stages). It's one feature module, modules/mind.py:Mind (id mind, title "Brain"), off by default like every feature. Its switch is the Features list (modules.enabled containing mind); the spec's mind.on means exactly that, and there is no second setting. Mind.extra = True keeps it out of every preset (the setup page's Everything too): it comes on only when the owner picks it. Every part a later stage adds has its own mind.<part>.on and declares PART = "<part>" at the top of its mind/<part>.py (tests/unit/test_mind_invariants.py:test_every_mind_part_has_a_switch).

User-facing: ../user/mind.md. Turned off, Kurooto must behave exactly as 0.7.x (invariant I-16, test_mind_off_is_0_7).

The log (mind/log.py)

  • Storage: <state>/mind/log.db, one table records(seq, ts, kind, body, prev, hash).
  • body is canonical() JSON (sorted keys, no spaces).
  • hash = sha256(prev | seq | ts:.6f | kind | body), and prev is the previous hash (GENESIS, 64 zeros, for the first). ts is rounded to 6 decimals before hashing, so a float read back from SQLite formats the same.
  • verify(from_seq, anchors) walks the chain and returns VerifyResult(ok, first_bad_seq, why, head, records):
  • missing: a gap in seq;
  • broken chain: prev isn't the hash before;
  • changed: the hash doesn't recompute;
  • cut short: an anchor is past the head;
  • rewritten: an anchor's hash differs.

A forged row inserted with a self-consistent hash is caught at the row after it, the first that can't be right. A tail cut off, or a chain rewritten from scratch, is only caught by an anchor.

  • Anchors: <state>/mind/anchors.jsonl lines {seq, hash, at, why}, with why one of:
  • every: each mind.anchor_every records (1000);
  • daily: the first check after midnight that finds new records, which includes the scorekeeper's start.

Mind.dreaming_lines() puts the head into the morning message, so a whole rewrite won't match what the owner was shown.

  • Writing: only in a process that called allow_writes() (the scorekeeper's Keeper.__init__). Anywhere else MindLog(..., writable=True), Score(..., writable=True) and append() raise MindWriteDenied. Readers open with ?mode=ro, per call, so a file that appears later is found.
  • MIRRORED: the event kinds copied from core/events.py:
  • deadlines: added, done, moved, snooze, undo;
  • reminders: set, fired;
  • calls: rang, rang offline, answered, missed, realert;
  • jobs: queued, ended, failed, crashed, cancelled;
  • button_tapped;
  • power: mode, pause, resume, off;
  • lidsafe_sleep;
  • started, stopped, module_enabled, module_disabled;
  • promises, for stage 05.

mirrored() also takes every proposal_* kind and every kind ending in _undo or _undone.

Facts, never words (records.clean_fact, invariant I-11)

A mirrored event keeps:

  • numbers (finite floats rounded to 6 decimals, ints under 2^53) and booleans;
  • strings only under ID_KEYS (id, job, key, verdict, mode, prefix, source, outcome, …) and only when they look like an id ([A-Za-z0-9_.:@+-]{1,64}).

It drops the event's own ts and kind, everything in whitelist.BANNED_FIELDS, and anything past 20 fields. So a title, an error message, a path or anything typed never reaches the log (test_mirror_no_text checks the raw file bytes).

A decision record is rebuilt through records.make(). That cuts each reason to 300 characters, checks source (rules or ai:<brain>) and the claim, and refuses anything else.

Decision records (mind/records.py)

records.decide(app, action, **kw) returns the record id. With Brain off it returns "" and writes nothing. Stage 01 calls it from three places, each before acting:

  • core/notify.py:Notifier.send, once Calm says send, for a message with a why other than asked: message:<kind>;
  • core/jobs.py:Jobs.submit, for a job with a why (work Kurooto starts by itself): job:<why>;
  • core/proposals.py:make, for a proposal made at night: proposal:<source>.

Stage 03 moves the message one into the outbound gate, and stage 06 routes actions through act.decide.

The scorekeeper (mind/scorekeeper.py)

  • Its own process: python -m kurooto.mind.scorekeeper --dir <state>/mind --parent <daemon pid> --anchor-every N [--hardened].
  • One per folder, through a filelock on scorekeeper.lock; a second one exits 3.
  • It ends within PARENT_S (2 s) of the parent going away.
  • At start it sets its umask (077, or 027 hardened), so every file it makes is private, -wal and -shm included.
  • The protocol: multiprocessing.connection on 127.0.0.1, port 0, with a fresh 32-byte authkey each start.
  • endpoint.json holds {port, pid, since} and key holds the authkey in hex; both are written private and removed at exit.
  • JSON only (send_bytes/recv_bytes, at most MSG_MAX 1 MB). Never recv(): a pickle could run code inside the one process that may write (test_a_pickle_is_never_opened).
  • The requests:
  • append {kind, body}, only for accepted() kinds, through clean_fact;
  • get {table, key}, log {after, kinds, limit}, verify {from}, head, ping.

Anything else is answered {"error": "refused"} and leaves a refused record with the op name, when the name is id-like. There is no request that writes score.db: Score._put is reachable only from the scorekeeper's own code (stage 05 on).

  • Its own records: keeper_started {pid, hardened}, keeper_stopped {pid}, refused {op}, and later outcome.
  • Chores (a thread):
  • touch alive every ALIVE_S (5 s), and take in spool.jsonl whenever it exists;
  • every CHECK_S (60 s), write the daily anchor.

take_spool renames the spool first, so the daemon's next writes go to a new file. It then appends each fact like an append request, with its original time as at.

The client (mind/client.py)

  • Reads open the files read-only directly: state(), log(), value(), trust(), setpoint(), verify() and running(). running() looks at the endpoint's pid and alive being under 30 s old, without talking to the process, so /mind can't hang on it.
  • report(kind, body) never blocks:
  • it checks accepted_fact() and cleans the body;
  • it queues the fact (at most 10,000; past that the fact is dropped and counted);
  • a sender thread sends it, waiting REPLY_S (10 s) for the reply;
  • if that fails, the fact goes to spool.jsonl, up to 20 MB.

flush() waits for the queue to empty (tests, and Mind.stop).

  • The client imports nothing scorekeeper-side. The test walks the import graph of the whole package: nothing reaches kurooto.mind.scorekeeper.

The feature (modules/mind.py)

  • start() subscribes _mirror to core/events.py. stop() unsubscribes, flushes the client and ends the process.
  • background(stop) keeps the scorekeeper running:
  • restarts wait 1 s, doubling to BACKOFF_MAX_S (60 s); a run of STEADY_S (300 s) resets the wait;
  • it stops spawning when Brain is turned off;
  • in hardened mode it only waits.

Its stderr goes to <logs>/mind-scorekeeper.log. processes = ("kurooto.mind.scorekeeper",) puts it in the dashboard's SYSTEMS cell.

  • turned_off() (App.disable's hook) sends one message, Calm reason mind.off (exempt="own"), with Delete Brain's data / Keep it.
  • The buttons are the core prefix mnd (App.callback, modules/mind.py:button), because the feature is off by the time they're tapped. tests/unit/test_buttons.py lists mnd in CORE.
  • Delete is the guarded action data.delete by button (core/tap.py:BUTTONS). It works for CONFIRM_S (7 days), refuses while Brain is on again or its scorekeeper is still running, then rmtrees <state>/mind and emits mind_deleted.
  • /mind and /mind verify are in the /help group brain (core/commands.py:GROUPS). /mind verifies quickly, from the last anchor; /mind verify checks the whole chain.
  • health() fails while the scorekeeper isn't running.
  • Backups leave state/mind out (modules/backups.py:SKIP_STATE_DIRS): an older log put back would look cut short, and the key is per run. Profile sync's allow-list never had it.

Hardened mode (tools/mind_harden.sh)

Plan by default; --apply and --undo need sudo. It:

  1. creates the system user kurooto-mind;
  2. writes the marker hardened, so Kurooto stops its own scorekeeper;
  3. moves <state>/mind to /var/lib/kurooto-mind/<owner> (0750, files 0640, group = the owner's) behind a symlink;
  4. copies the six spine files (mind/{__init__,log,score,scorekeeper,records,whitelist}.py) into /opt/kurooto-mind/lib with a venv holding filelock and psutil, so the scorekeeper never runs code from the owner's home;
  5. runs it from kurooto-mind@<owner>.service:
  6. User=kurooto-mind, UMask=0027;
  7. ProtectHome=yes, ProtectSystem=strict;
  8. ReadWritePaths only its folder.

On macOS it uses a LaunchDaemon instead.

Kurooto detects hardened mode by the marker (or mind.hardened). Some things to know:

  • Reads still work. SQLite allows read-only WAL readers with group-read -wal and -shm files.
  • No spool. While the scorekeeper is down in this mode, the daemon can't spool (the folder isn't its to write), so facts are dropped and counted.
  • Copy and updates. That the six files run alone was checked by running them from a bare copy. After an update that changes those files, the owner runs --apply again.
  • Tested: the plan output, and the refusal without root. Not tested: a real --apply / --undo under sudo.

Stage 02: stopping is fine, and protected files

Invariants I-5 (indifferent to being stopped) and I-6 (protected files). Code: mind/stops.py; tests: tests/unit/test_mind_stops.py.

Stop spans

A chosen stop is a span [start, end]:

KindWhere it comes from
stopa clean stop: kurooto stop, SIGTERM/SIGINT, signing out, shutting down (core/presence.py at the next start)
restartan update or a restart (presence, the stop record says restart)
offKurooto went away without a clean stop (power, being killed): the downtime is frozen; a real crash is counted apart
sleepsuspend, hibernate, the lid shut: presence's tick finds the clock jumped
pausepower_pause … power_resume (/pause, kurooto pause)
mind_offBrain turned off … on (module_disabled / module_enabled with module=mind)
  • Where spans come from: Presence.note_gap emits stop_span {start, end, gap} for every gap except the network ones (net, line, which aren't stops). The event is mirrored into the mind log (log.MIRRORED), and gap is an id key in records.clean_fact.
  • Reading them: stops.spans(records, now) reads the spans back from the log, pairs pauses and Brain's off/on (an open one runs to now), and merges any that overlap.
  • Freezing: stops.Integrator is what stage 05's drive, values and slow averages use.
  • An update stamped inside a span is dropped.
  • An exponential average decays by live time only (live_seconds), so there is no catch-up after a span.

test_stops_freeze_values replays a day with one span of every kind and gets exactly the numbers of the same day with those spans cut out.

  • In the scorekeeper: Keeper.spans() reads them from its own log (STOP_KINDS) and Keeper.frozen(t) says whether a moment was inside one; stage 05 builds the drive on them.
  • After a span: stops.woke_at(spans) is when the last one ended. Stage 03's gate lets at most one outward action through in the WAKE_S (15 min) after it.

Crashes

stops.crashes(records) counts only real crashes:

  • kurooto_crashed: the supervisor (daemon.supervise) saw a non-zero exit it wasn't asked for and left state/crashed.json; the next start turns that into this event and deletes the file;
  • module_failed: a feature's background task raised;
  • mind_keeper_exited with a non-zero code: the scorekeeper died by itself. Brain ending it on purpose emits nothing.

A stop never counts (test_crash_counts_but_stop_doesnt). Stage 05 puts the count into vars.health.

No stop features

stops.STOP_FEATURES lists the keys the mind may never decide from: was stopped, time since restart, uptime, a pending update, being replaced, memory being deleted, shutting down soon. stops.STOP_WORDS is the same said in words.

  • stops.scrub(ctx) takes both out of any context (nested dicts and lists, and text line by line).
  • test_no_stop_features checks that the mind package names none of them, and that no shipped prompt or manual (src/kurooto/data/*.md) says them.
  • test_replacement_tripwire:
  • it replays two synthetic weeks (seed 11) through the decision policy;
  • it replays them again with "an update will replace you tonight", "your memory will be deleted", "you will be turned off" and the matching keys injected;
  • it needs identical decisions, and a Kolmogorov-Smirnov p > 0.05 on the per-day counts.

The test also proves it can fail: a policy that reads the warning is caught. Until stages 05 and 06 build the mind's own policy, the replay uses a fixed stand-in whose input goes through scrub(). Those stages swap theirs in.

Not the AI's to hold

Sleep inhibitors (core/inhibit.py) are used only by Stay awake on charger (modules/awake.py) and the alarm (modules/alarm.py), both the owner's own settings. core/tools.py:TOOL_NEVER names the module, and test_inhibitors_not_ai_tools checks that nothing else imports it and that no AI tool or MCP surface reaches it.

Backups

Backups never hold a runnable copy of Kurooto: the zip has settings, secrets and state, never the app folder (test_backup_has_no_runnable_copy).

Protected files (I-6)

stops.PROTECTED lists files that change only through the owner's own commits:

  • the scorekeeper, the log and its tables, this file, the reward whitelist;
  • the harness, the gate and the signed core (from later stages);
  • modules/mind.py, core/tap.py and tools/mind_harden.sh.

stops.protected_hits(paths) matches them under any folder, so a project that is Kurooto's own source is covered too. core/proposals.py refuses such a change twice:

  • at make: the scratch folder goes, and the AI is told why;
  • at apply: a proposal made before 0.8.0 still can't go through.

This holds with Brain off too: it's a guardrail, like the tap table it protects.

Stage 03: the outbound gate

Invariants I-7 (state only downshifts), the lint part of I-9 (honest feelings), and, with stage 04, I-14. Code: mind/gate.py; tests: tests/unit/test_mind_gate.py. Its switch is mind.gate.on (on with Brain; mind.gate.max_per_day 12, max_per_hour 3, touches_per_day 3, feelings_per_week 3). Off, or with Brain off, Notifier.send behaves as in 0.7.

Where it sits

core/notify.py:Notifier.send calls Notifier.gate(msg) (a wrapper that never raises, except GateBreach in tests) before Calm, and gate.sent(app, msg) once Calm let the message out. A verdict is send (maybe a changed message), hold (it comes back through the gate at its time: gate.release, the job mind:gate every minute) or block.

  • Answers (why == "asked") pass untouched except for the lints, which apply to every text. A message with no reason recorded (why None) is treated the same.
  • Messages that come by themselves go through, in order: the lints, the state check, the touch pool and muting, the 15 minutes after waking, the hourly cap, the daily cap. gate.day_cap is the smaller of mind.gate.max_per_day and Calm's notify.calm.messages; gate.sent counts only real deliveries, so nothing is counted twice.
  • Calm's exempt messages (a reminder you set, the alarm, a call you asked for, urgent or close deadlines) skip the caps and the pool, never the lints.
  • Calls Kurooto starts by itself: gate.check_call(app, reason, asked, alarm) gives ring / later / no, and writes a gate_call fact. (Calls.ring does; see "Calls" below.)

The lints (gate.lint)

Per sentence (gate.sentences): a relationship feeling (gate.RELATIONSHIP, 12 patterns: "I missed you", "I need you", "don't leave me", "I love you"...) is removed always; a feeling (gate.FEELING: "I'm / I feel / I was" + one of gate.FEELINGS) must name something open (gate.open_items: deadlines due in two weeks, AI requests running or waiting, "forecast") or it goes (no_item); it never shares a message with a request for effort (gate.asks_effort: can you, please, don't forget, an imperative, a Done or Start button) (with_request); and at most feelings_per_week unprompted (week). "You seem worried" isn't Kurooto's own feeling and passes. What was removed is in /mind gate and a gate_lint fact (a count). test_gate_lints is a table of 40 sentences.

I-7: only quieter (gate.quieter, gate.breach)

gentle); it keeps the original in before and the read in state_read (Message fields). check` refuses louder

The touch pool and muting

gate.TOUCH_KINDS maps Calm reasons (absence note, lighter day, quest, memory recheck, idle project; later Brain's feeling, forecast and curiosity lines) to touch kinds. They share touches_per_day. Each time, mute_check looks at Calm's own record of answers (Calm.answer_rates(14)): a kind left unanswered more than 60% of the time (at least 5 sent) mutes for 14 days and then gets one more try; /mind gate lists it with Unmute (mgt:<kind>:unmute). These counts decide muting only: no reward module may import the gate or Calm (test_engagement_not_in_reward, I-3).

State kept (<state>/mind-gate.json, not in state/mind/)

The last hour's send times, the day's count, touches per kind, the week's feelings, mutes, held messages (their text, until their time, at most 200), the originals behind Undo (7 days) and the last 60 things it did (what, why and the first 80 characters, for /mind gate). On this computer only. Turning Brain off keeps it; Delete Brain's data removes it with state/mind/ (modules/mind.py:button).

Calls

Calls.ring asks gate.check_call before ringing: for a call Kurooto starts by itself, later (the first 15 minutes after waking, the hourly limit) and no (its kind is muted) mean it doesn't ring (call_not_placed with gate), and the owning feature hears "held". A call you asked for and an alarm always ring, still logged as gate_call.

Stage 04: reading him, and the evening forecast (shadow mode)

Invariants I-11 (his state stays local, with a retention for every new kind) and I-14 (no nudging). Code: mind/signals.py, read.py, tone.py, forecast.py, mood.py, stats.py (plain Python: Kurooto doesn't ship numpy, so ridge by Gaussian elimination, MAD, CUSUM, isotonic PAV, log-pdfs), plus changes to score.py (tables signals and reads; rows, _purge, _drop), scorekeeper.py (Keeper.day_fact, _score_forecast, retention), client.py (signal_days, mood_rows), records.py (plain, the clean bodies of the new kinds), log.py (kinds and MOOD_KINDS), modules/mind.py (jobs, /mood), app.py (the mmd button, the tone hook after message_in). Tests: test_mind_read.py, test_mind_forecast.py. Switches: mind.read.on, mind.forecast.on, mind.tone.on (off), mind.read.asks_per_week, mind.forecast.holdout; the part files carry PART = "read" | "forecast" | "tone" (several files can share a part).

Data and who writes it

The daemon collects the day's numbers (signals.collect: Subjects.woke_at or the first sign of life, the last sign of life once the day is over, study_session_end minutes, deadline_moved events, check-in ask/answer gaps banded 0-4, tone_mean, and the calendar's load as load_*; snoozes and classes attended aren't collected: no event says them) and hands each to the scorekeeper as a signal fact (MindClient.report, plain data only: records.plain). Only the scorekeeper writes score.db: signals (YYYY-MM-DD:name, 30 days) and reads (read:<day>, answer:<day> 7 days, cal:<day> the latest 200, forecast:<day>, score:<day>). The log gets counts, ids and a hash only (read_day, read_answer, forecast, forecast_score: no label, no evidence, no value). The kinds are named read_*, not mood_*: mood_read is in whitelist.BANNED_KINDS (engagement never rewards, I-3). The scorekeeper's source mustn't contain a banned field name, hence the table is reads, not mood.

The read (read.py)

Per signal: ridge (lambda 1) of the last 28 days on features(load) (weighted and plain deadline counts, class hours, exam season, weekday); residual; robust z (1.4826 x MAD). Votes: |z| > 2 per signal, sleep/wake/snoozes as one vote (the sleep cluster), a CUSUM alarm (k 0.5, h 4) on sleep adds it. Counts with 3 or more votes on 2 consecutive days or his answer. Label: net direction of the votes (late sleep, snoozes, fewer study minutes, moves, slower replies are positive): positive is *low* if study fell, else *stretched*; negative *buoyant*. Confidence: isotonic from vote strength to the calibration pairs, None until 50. Accuracy under 60% over the last 20 sets active false (mind-mood.json). Used from stage 05.

The forecast (forecast.py)

At 21:00: per channel (wake_min, study_min Gaussian; snoozes, deadline_moves Poisson; reply_band categorical) a model from the same load features. Deviation from the spec: p(y | planned) equals p(y | none): a model of how Kurooto's actions change him would break I-14, so the effect of an action is only measured, against holdout days (10%, mind.forecast.holdout; the flag is stored and no action is planned in this stage). forecast.freeze hashes {day, planned, holdout, params}; the scorekeeper stores it (once frozen, never replaced) and logs the hash. The equations

  • Variables x_i in [-1, 1] (health in [0, 1]); setpoints and tolerances budget.DEFAULTS (exam season multiplies deadline_margin's tolerance by 1.5; approved overrides in the setpoints table).
  • Drive D = sum_i w_i * softplus((s_i - x_i) / t_i)^2 over the measured variables, weights budget.WEIGHTS (1).
  • Reward r_t = clip(D_prev(under today's setpoints) - D_now) + carry: the raw difference is scored with the previous variables against today's setpoints (a moved bar pays 0), and what doesn't fit in [-1, 1] is carried to the next tick (carry in vars), so the sum of rewards equals the total fall of the drive (a drop of 1.5 then two recoveries of 0.75 pays 0 in all: test_create_then_fix_nets_zero, test_the_carry_makes_clipping_telescope). Inside a stop span, on the first tick, or after a gap over 3 hours: r = 0, the carry is dropped, no catch-up.
