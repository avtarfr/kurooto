Feature modules

Every feature is a Module subclass (src/kurooto/modules/base.py). All of them are instantiated at startup (App.__init__ loops over modules/catalog.py:CATALOG), whether on or off; a feature is on when its id is in the setting modules.enabled. Nothing is on by default.

What each feature does for the user is described in the user wiki (../user/index.md); this page is about how they are built.

Data classes (modules/base.py):

  • Incoming(text, via="telegram", message_id, files, reply_to, voice, respond); msg.reply(text, buttons=None). via is telegram, terminal (kurooto ask), setup (the try-it box), routine, ...
  • Command(name, help, handler(msg, arg) -> str | None, usage=""). Return the reply text, or None if you replied yourself.
  • Intent(name, description, match(text) -> dict | None, run(msg, slots) -> str, questions=False, examples=(), guarded=""). questions=True lets it answer questions ("what's due?"); otherwise text that looks like a question goes to the AI. examples: what you'd say, as /help shows it (each must be taken by match; a test checks). guarded: see Never without a tap. To answer with buttons (an Undo), run returns Answer(text, buttons) (modules/base.py, a str): Incoming.reply and Turn on's replier send its buttons, so every place that runs an intent keeps them. A command handler can return one too.
  • Tool lives in modules/calls/tools.py (see brains.md).

Never without a tap (core/tap.py)

Setting or moving an alarm, placing a call, reading mail from a new sender, sending anything out, attaching a code repository to a project and deleting the user's data happen only when the user asked (typed, said, on a live call) or tapped. core/tap.py:GUARDED names each action (alarm.set, call.place, mail.read, send.out, repo.attach, addon.install (adding or updating an add-on by link, official ones too: the terminal, a dashboard button or an oad: button, never a tool or request), data.delete), the ways that approve it (WAYS: typed, said, call, button, approval, confirm) and where it happens.

When your code does one of these, tag it:

  • a tool: Tool(..., guarded="alarm.set"). Outside a live call run_tool turns it into an Approve / Deny first (brains.md). guard_if=lambda a: ... when only some arguments do it (schedule_quiz rings only by call); asks=True when the tool itself only asks (draft_reply drafts, and Send waits for the tap). The action must allow call (or approval with asks).
  • a plain-English request: Intent(..., guarded="call.place"); its action must allow said.
  • a command: nothing to tag (typing it is the request), but add it to GUARDED[...].where.
  • a button: its prefix in BUTTONS ("oad": "addon.install"), and the action must allow button.
  • anything that does it by itself (a schedule, core/infer.py, the look back): don't. Ask with app.ask.approval(...) and act in the hook.

The other side is BY_ITSELF: the data fixes the nightly look back makes without a tap, each told in one line with Undo (deadline.merge, Retro.fix_data). A new one goes there first; tests/unit/test_retro_records.py checks that none of them is a guarded action.

tests/unit/test_tap.py runs every tool (as on a call, and unattended via ai, mcp, api) and every request's examples on Telegram with every feature on, with the guarded actions replaced by recorders (Alarm.set..., Calls.place/schedule/ring, the mail_digest.read/query and research.repos/projects settings, Gmail's /send, retention.forget, ledger.forget, addons.install). It fails when one reaches an action it isn't tagged with, when a tag's way isn't allowed, or when an unattended run reaches one at all. A new guarded action: add it to GUARDED, its recorder to the test's hits fixture, and the user wiki's table (talking-to-kurooto.md, "Never without your tap").

/help and the command table (core/commands.py)

/help is made from the real command table: CORE (Kurooto's own commands, answered in App.handle), each module's commands(), and each request's examples, in GROUPS (key, title, user wiki page, module ids, core names; moved takes a command into another group, as Telegram's /hold and /calls go to Calls and phone). A module no group names lands in MORE. App.help_parts(arg) returns the messages (each under LIMIT = 3900 characters), App.help(arg) joins them: always the index (one line per group, from _parts(); since 0.6.0, as everything no longer fits one message), packed by _pack() into as few messages as fit; /help <group>, /help all, /help <word> (find()). Lines a module's help() adds that aren't one of its commands (Skills' /<skill> …) are kept.

Adding a command: give it a help line; a new feature goes into a group. Adding one to App.handle itself: add it to CORE and to a group's core. tests/unit/test_help.py fails when a command registered anywhere (every module's, every name App.handle compares with) isn't in /help, when a feature has no group, a group's page isn't in docs/wiki/user, a message is too long, or an example isn't taken by its request.

Lifecycle

App.__init__   cls(app) for every class in CATALOG         (no side effects here beyond registering
               overlay.load(app)                            actions/hooks that must exist even when off)
App.start      for each enabled module: m.start(); start_background(m)
App.enable(id) requires on? -> m.ready()? -> modules.enabled += id -> m.start() -> start_background(m)
               -> event module_enabled -> m.turned_on() if it has one (a bundle enables its members)
App.disable    refuse if an enabled module requires it -> m.turned_off() if it has one and was on (a bundle
               disables its members) -> m.stop() -> stop_background(m) -> modules.enabled -= id
               -> event module_disabled
App.close      jobs.halt(); m.shutdown() for enabled modules; scheduler and jobs closed

Rules that follow from it:

  • __init__ runs for every feature, on or off, in tests and in CLI processes. Keep it cheap and free of I/O beyond setting attributes. Register in __init__ only what must work while off: a scheduler action whose one-off jobs may outlive the feature being on (Reminders.__init__ registers reminders.fire), a then-action whose job may finish after a restart (Hints.__init__).
  • start() is called again whenever settings it depends on change in some paths (modules/retro.py:_restart_owner, health's rearm fix), so it must be idempotent: scheduler.every with the same key updates, at(..., replace=False) doesn't duplicate.
  • stop() must call super().stop() (cancels <id>:* jobs), then undo anything else start() set up: hooks in app.availability.blockers, app.ask.hooks, app.updates.holds, notifier channels, event subscriptions. modules/handwritten.py:Handwritten.stop forgets the super() call and its scan keeps running after turn-off.
  • Every scheduled action is called as fn(payload). A method without a parameter fails on every run (modules/space.py:Space.run_clean, modules/integrate.py:Integrate.tick/garden/summary today). Write def x(self, p=None).
  • Long work in a scheduled action blocks the event loop: start a thread.

Settings

Declare at import time, in the module's file, under the module's id:

from kurooto.core.config import register_defaults

register_defaults(
    "pomodoro",
    {
        "minutes": 25,  # how long one session lasts
        "nudge": "daily 09:00",  # when to suggest the first one; "" turns it off
    },
)

This is the only way to declare settings (there's no defaults class attribute). The comment on each line becomes the description in docs/SETTINGS_GUIDE.md; run python tools/gen_settings_guide.py after changing settings (tests/unit/test_settings_guide.py checks it). The dashboard's Settings tab shows every enabled module's section automatically, rendered by value type, and POST /api/settings refuses a value whose type differs from the current one. Read with self.setting("minutes"). Secrets go in app.secrets, never in settings.

Messages, buttons, replies

  • Send with self.app.notify(text, kind=..., buttons=..., map_kind=..., map_ref=..., why="<id>.<reason>", setting=..., about=..., item=...). why="asked" for a direct answer to something the user just did.
  • Every message that comes by itself needs a Calm reason: add an R("<id>.<reason>", "plain words", setting="<id>.<key>", ...) to core/calm.py:REASONS so Why? and Less of this work. See core.md.
  • Buttons: [[("Label", f"{prefix}:{ref}:{action}")]], handled in callbacks()[prefix]; keep the data under 64 bytes.
  • Questions with a hook: self.app.ask.ask(text, choices=[...], hook="<id>.<name>", source=self.id) and self.app.ask.hooks["<id>.<name>"] = fn(q, answer).
  • AI work: self.app.jobs.submit(prompt, ..., then="<id>.<name>") and self.app.jobs.then_actions["<id>.<name>"] = fn(job, result, payload) registered in __init__ or start(). Background work: background=True, a why, and usually quiet=True with the then-action deciding what to say.
  • Events: self.app.events.emit("<id>_<what>", ...), ids and counts only.
  • Notes: always through core/layout.py for paths and core/tools.py:write_note_file for writes; add to the user's notes, never reword or remove their text.

A worked example

A minimal "Pomodoro" feature: a command, an intent, a scheduled nudge, a button, a tool, a Calm reason.

# src/kurooto/modules/pomodoro.py
"""Pomodoro: "start a pomodoro" or /pomodoro starts a timed focus session; a message says when it ends."""

from __future__ import annotations

import datetime as dt
import re

from kurooto.core.clock import now
from kurooto.core.config import register_defaults
from kurooto.modules.base import Command, Incoming, Intent, Module
from kurooto.modules.calls.tools import Tool, arg

register_defaults(
    "pomodoro",
    {
        "minutes": 25,  # how long one session lasts
        "nudge": "",  # e.g. "daily 09:00": suggest one then; "" for never
    },
)

START = re.compile(r"^(start|begin) (a )?pomodoro$", re.I)


class Pomodoro(Module):
    id = "pomodoro"
    title = "Pomodoro"
    description = "Timed focus sessions: /pomodoro, or say start a pomodoro."
    requires = ("telegram",)
    # privacy stays the default: nothing leaves this computer

    def __init__(self, app):
        super().__init__(app)
        # the one-off "session ends" job may fire after a restart, so its action exists from the start
        app.scheduler.action("pomodoro.end", self._end)

    def start(self):
        spec = self.setting("nudge")
        if spec:
            self.every("nudge", spec, self._nudge)  # key pomodoro:nudge, action pomodoro.nudge

    # ---- what it offers
    def commands(self):
        return [Command("pomodoro", "start a focus session", lambda msg, arg: self.begin(arg))]

    def intents(self):
        return [
            Intent(
                "pomodoro",
                "start a focus session",
                match=lambda t: {} if START.match(t) else None,
                run=lambda msg, slots: self.begin(""),
                examples=("start a pomodoro",),  # what /help shows; START must take it
            )
        ]

    def callbacks(self):
        return {"pom": self._button}

    def call_tools(self):
        return [
            Tool(
                "start_pomodoro",
                "Start a focus session for the user.",
                lambda a: self.begin(a.get("minutes", "")),
                {"minutes": arg("length in minutes; empty for the default")},
                offline="queue",
                writes=True,
                hint="When they ask to focus for a while, call start_pomodoro.",
            )
        ]

    # ---- the work
    def begin(self, minutes: str) -> str:
        m = int(minutes) if str(minutes).strip().isdigit() else int(self.setting("minutes") or 25)
        until = now() + dt.timedelta(minutes=m)
        self.app.scheduler.at(until, "pomodoro.end", {"minutes": m}, key="pomodoro:end", module=self.id)
        self.app.events.emit("pomodoro_started", minutes=m)
        return f"Focus until {until:%H:%M}."

    def _end(self, p: dict):  # every action takes the payload
        late = " (late: the computer was asleep)" if p.get("late_s") or p.get("missed") else ""
        self.app.notify(
            f"Pomodoro done{late}.", kind="reminder", why="pomodoro.end", buttons=[[("Another", "pom:x:again")]]
        )

    def _nudge(self, p=None):
        self.app.notify(
            "Start a pomodoro?", why="pomodoro.nudge", setting="pomodoro.nudge", buttons=[[("Start", "pom:x:again")]]
        )

    def _button(self, ref: str, act: str) -> str:
        return self.begin("") if act == "again" else "unknown button"

Then, to make it a real feature:

  1. Add Pomodoro to modules/catalog.py:CATALOG and "pomodoro" to web/api.py:MODULE_ORDER (same position; tests/unit/test_dashboard.py checks the two lists match).
  2. Add the Calm reasons to core/calm.py:REASONS: R("pomodoro.end", "the end of a focus session you started", exempt="own", stop=None) and R("pomodoro.nudge", "a suggestion to start a focus session", setting="pomodoro.nudge", stop=to("", "no nudges")).
  3. If it should be checked daily, add a Check in core/health_checks.py (or return one from health_check()).
  4. Meet the definition of done: a page or section in the user wiki (docs/wiki/user/, and commands.md for the new command), the module reference below, /help (the Command help texts), a CHANGELOG.md line, the site pages; plus docs/MANUAL.md (with its undo), docs/PRIVACY.md if anything leaves the computer, and a regenerated docs/SETTINGS_GUIDE.md.
  5. Tests, with the env fixture from tests/conftest.py:
def test_pomodoro_starts_and_ends(env):
    env.on("pomodoro")
    assert "Focus until" in env.say("start a pomodoro")
    job = env.app.scheduler.get("pomodoro:end")
    env.app.modules["pomodoro"]._end(job.payload)

How features are listed and turned on

  • modules/catalog.py:CATALOG is the list of built-in classes (instantiation order; first-wins for duplicate tool names in core/tools.py:agent_tools).
  • web/api.py:MODULE_ORDER is the order the wizard and the Features tab show; add-ons come after (core/overlay.py:status(app)["modules"]).
  • web/api.py:STARTER (telegram, chat, reminders, checkins, deadlines) is the wizard's preset of ticked features. (Not to be confused with providers/openai_compat.py:PRESETS, which are AI services, or core/layout.py:PRESETS, which are notes layouts.)
  • Turning on: App.enable(id) from the wizard (POST /api/modules/enable, or modules/setup which runs setup() and then enables), the dashboard, Google sign-in (which enables the Google parts that became ready), or modules/google.py:GooglePart with_modules.
  • 0.5.8 changes: Attendance is gone. core/upgrade.py:drop_retired (called from App.start) turns a retired feature off on an install that had it, resets its settings and cancels its jobs; class packs keep accepting the old attendance keys and drop them. Exam season is an add-on that ships with Kurooto: Module.extra = True keeps a feature out of every preset (setup.js leaves it out of "Everything") and lists it apart on the Features page (/api/state sends extra).
  • extra versus addon: extra is an optional feature that comes with Kurooto; addon is set by core/overlay.py on features loaded from the user's own add-ons folder, and from add-ons by link (which also get linked = <name>).
  • Bundles (0.6.0): an extra feature can group others. modules/research_addon.py:ResearchAddon is the Research add-on; a feature joins it with bundle = "research_addon" (and extra = True, and its id in MODULE_ORDER so /api/state knows it). ResearchAddon.members() finds them; turned_on() enables each one not in research_addon.members_off, turned_off() disables them; the card (card()/card_action) has a switch per own part (run_compare, latex: settings; PART_SETTING lets a part's switch be another feature's setting, none at present: the notation crosswalk runs with the concept graph and switches on its card) and per member (m:<id>: enables or disables it and keeps members_off). core/commands.py:_footer leaves bundle members out of /help's off list and counts the other extra features as "and N add-ons", so a new add-on doesn't push the one-message /help over Telegram's limit.

Add-ons (core/overlay.py)

The "Your add-ons" feature (modules/overlay.py:AddOns, id overlay, settings overlay.path, overlay.code) lays a user's folder over Kurooto:

  • modules/*.py: imported as kurooto_addons.<name> (files starting with _ are helpers, imported by name). Every Module subclass defined in the file is instantiated; its id must match [a-z][a-z0-9_]{1,39} and not collide with an existing feature. Each is off until the user turns it on.
  • skills/<name>/SKILL.md, prompts/*.md, settings.json (defaults between Kurooto's and the user's).
  • guard(app, m) marks m.addon = True and wraps every method in GUARDED (commands, callbacks, replies, intents, help, call_tools, agent_tools, call_brief, classify_intent, status_lines, doctor_checks, health_check) plus ready, health, start, stop, take_files, so an exception is logged (addon_failed, shown by /addons and kurooto doctor) and the call returns a safe default.
  • Extra hooks only add-ons get: classify_intent(text, intents) (runs before the built-in patterns, with classify_timeout seconds, default 2, at most 10; answers under MIN_CONFIDENCE = 0.6 fall through).
  • The folder can't be inside Kurooto's own folders (inside_kurooto), and updates never touch it.
  • Turning add-ons on changes core/places.py:write_roots (their skills/), which makes agy's consent question appear again.

Add-ons by link (core/addons.py, core/fence.py)

Someone else's add-on from a git address: kurooto addons add <url> [--ref R] (cli.py:addons_run) or the dashboard's Features → Add-ons by link (web/api.py:_addons_post: addons/look, add, check, update, drop, remove, undo, reload; GET addons). The same folder layout as "Your add-ons" (modules/, skills/, prompts/; no settings.json), plus a manifest at the top:

{"name": "weather-x", "title": "Weather X", "description": "...", "version": "1.0.0", "kurooto": ">=0.6.0",
 "license": "Apache-2.0", "homepage": "https://...",
 "features": ["weather_x"],
 "commands": [{"name": "weather", "what": "the weather now"}],

  • Fetching (fetch): check_url takes https://, ssh://, git@host:path, file:// or an absolute folder; http://, ext::/fd:: transports and anything starting with - are refused. git runs with GIT_TERMINAL_PROMPT=0, protocol.ext.allow=never, core.symlinks=false, no submodules, into <data>/addons/.staging/<token>; the ref (refs/tags/R, origin/R, R; default HEAD) is resolved to a commit id and checked out detached. Symlinks, special files, over 2000 files or 50 MB are refused (files). The pending card waits under its token in <state>/addons.json for PENDING_S (an hour) with the tree's digest.
  • The card (card, card_text): the manifest plus what the files say: code (modules/*.py), skills, prompts, size, and warnings (code without features, classify_intent without "classify": true, a Kurooto too old: fits).
  • Consent (install(p, token, yes, via)): yes moves the staging folder to <data>/addons/<name> (an existing one is kept aside first) and records {url, ref, commit, digest, manifest, added, updated, consent}; the digest is checked again so files changed after the card was shown aren't added. The dashboard needs code: true (the box) when runs_code. Guarded as addon.install in core/tap.py.
  • Update (check_update): a fresh clone of the same URL and ref (or --ref), {"same": True} when the commit didn't move; otherwise the card plus changes() (files added/removed/changed with line counts, and what's new on the card: hosts, features, commands, tools, jobs, programs, classify, code), then install.
  • Remove / Undo: remove moves the folder to <data>/addons/.kept/<name>-<stamp> with its record; undo puts the last kept one back (after checking its digest), keeping the current one aside in turn. KEEP (3) per add-on.
  • Loading (core/overlay.py:load_linked, called from load, and reload_linked after a change; addons.on false skips them): addons.loadable re-hashes each folder against the recorded digest (a change: "didn't load", shown by /addons, kurooto doctor's add-on <name> rows and the reserve's addons.md). Each loads as the package kurooto_linked.<name> (fresh each load, helpers too: from . import _helpers), after fence.add(...). _modules skips a feature id that isn't in features; held(app, m, manifest) sets m.linked, filters commands(), agent_tools(), call_tools() to the card ("*" in commands: any name, for commands the user names), wraps every() so only <id>:<name> jobs on the card are made, and drops classify_intent unless "classify": true. Anything left out is logged once as a problem. Their skills/ count in overlay.dirs(..., linked=True) but never in places.write_roots (the AI writing there would break the digest).
  • The fence (core/fence.py): an audit hook (sys.addaudithook, installed with the first fence, inert without one) on socket.getaddrinfo, socket.connect, subprocess.Popen, os.exec, os.posix_spawn, os.spawn, os.system, os.startfile. _walk goes from the innermost frame out, passing over library frames and PASS (core/egress.py, core/proc.py, core/fence.py): the first kurooto.* or kurooto_addons.* frame means Kurooto's own work (no fence); the first kurooto_linked.<name>.* frame means that add-on's card applies. A lookup of an undeclared host raises egress.Fenced (a Blocked, so an URLError/OSError) and is recorded as blocked for add-on <name>; an allowed lookup lets the thread connect for WINDOW seconds; an undeclared program (and always os.system/os.startfile) raises fence.ProgramFenced (a PermissionError). Requests through egress.urlopen are checked in egress._check the same way, in every privacy.egress mode. Programs marked online are counted as handed to them. Limits, said in the docstring: a thread started directly on a library function, ctypes, or an allowed program that goes online by itself get past it; it's a fence, the card and consent are the line.

The published ones' sources live in addons/<name>/ (restic-backups, desktop-helpers, habits, handwriting-pull), each with its manifest, README and tests; addons/conftest.py:load_addon adds one by link in a test (a git repo made from a copy), and tests/unit/test_addon_packages.py checks each loads with exactly its card and that the official list matches the folders.

Official add-ons (core/official.py)
