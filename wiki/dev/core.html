Core services

src/kurooto/core/ holds everything features share. App.__init__ (app.py) builds the services in this order: Paths → Settings → Secrets → egress.attach → Events → Availability → Scheduler (with gates) → Notifier → Power → AboutYou → Quota → Jobs → Updates → Ask → Presence → Health → Calm → Keep → Rhythm → every module in the catalog → add-ons. Anything a module needs is reached through self.app.<service>.

Settings

core/config.py.

  • Defaults: every section is declared by register_defaults(section, dict) at import time of the module that owns it (e.g. register_defaults("jobs", {"stuck_min": 10}) at the top of core/jobs.py). Calls for the same section merge (merge). It's the only way (Module has no defaults attribute), and tools/gen_settings_guide.py reads only these calls.
  • User overrides: <config>/settings.json holds only what the user changed. Settings.all() is merge(defaults, add-on layer, user), so a new default in an update reaches everyone who didn't change that key.
  • Add-on layer: set_layer() (called by core/overlay.py:load) lays an add-ons folder's settings.json between the defaults and the user's file; it can't set modules, overlay or profile (overlay.NO_DEFAULTS).
  • API: get("a.b.c", default), set("a.b", value) -> old (rewrites the user file with jsave), reset("a.b") (drops the override). Dotted keys address nested dicts.
  • Settings reads the file on every get; there is no cache and no cross-process lock, so the CLI and the daemon can overwrite each other's concurrent set. Change settings in the daemon (the API's POST /api/settings or a module method), not by editing the file while it runs.
  • Sections and where they are registered (the full list with every key and default is generated into docs/SETTINGS_GUIDE.md by tools/gen_settings_guide.py; tests/unit/test_settings_guide.py fails when it's stale, so regenerate it after adding or changing a setting):

Secrets

core/secrets.py:Secrets. Never in settings.json.

  • The OS keychain through keyring (service kurooto), else <config>/secrets.json (mode 0600).
  • The file is used when there is no usable keyring backend, when KUROOTO_HOME is set, when KUROOTO_SECRETS=file, or when the marker <config>/secrets-in-file exists (keep_in_file(True, names), used by core/autostart.py when Kurooto starts at boot on Linux, before the keychain is unlocked).
  • API: get(name), set(name, value), delete(name), names() (file only: the keychain can't be listed).
  • Names in use include telegram.token, web.token, gemini.api_key, <brain>.api_key, google.client, google.tokens[.<account>], calendar.ics, calls.call_secret, calls.connector_secret, calls.ntfy_topic, calls.ntfy_key, calls.vapid_jwk, calls.vapid_public, calls.github_token, notes_sync.token, profile.token, profile.key. diagnostics.py:KNOWN_SECRETS lists the ones the bundle redacts; add new names there.

Scheduler

core/scheduler.py:Scheduler, SQLite <state>/schedule.db, so jobs survive restarts and sleep.

  • action(name, fn): register a handler. Every handler is called as fn(payload) (a dict); it may be async. A bound method that takes no argument fails with TypeError on every run. Write def tick(self, p=None) or wrap it (lambda p: self.tick()).
  • every(key, spec, action, payload=None, *, module="", misfire="coalesce", respect="none"): a recurring job. Calling it again with the same spec keeps the job's next run; a changed spec reschedules.
  • at(when, action, payload=None, *, key=None, module="", replace=True, grace_s=43200, respect="none") -> key: a one-off. Naive datetimes are local time. replace=False leaves an existing key alone (a debounce).
  • cancel(key), cancel_prefix(prefix), get(key), jobs(prefix), due().
  • Specs (next_after), in you.timezone: every 10m, every 2h (at least a minute), hourly, daily 05:00, daily 07:00,13:00,19:00, weekly sun 19:30. A bad spec raises ValueError.
  • run_forever(stop) runs tick() and sleeps until the next job, at most 30 s, so clock jumps are noticed. _poke() wakes it when a job is added.

What tick() does with each due job, in order:

  1. Hold (Scheduler.hold = Power.hold): in saver or paused mode a job whose module may not run is pushed an hour and recorded in power-held.json; Power.release() runs them the moment the mode allows. Jobs with module="" are held only when paused.
  2. Gate (respect): "quiet" uses Availability.quiet_gate, which postpones to the end of focus time, not the quiet.json "no calls" window: every job that uses it sends a message (check-ins, quizzes, the morning lists), and "no calls" lets messages through while focus holds them; "call_block" uses Availability.call_gate (no built-in job uses it). Postponed jobs keep their key.
  3. Misfire: a one-off later than its grace_s gets payload["missed"] = True; later than 120 s gets payload["late_s"]. A recurring job with misfire="skip" more than 120 s late doesn't run (no built-in job uses skip); coalesce runs it once. Either way the next run is computed from now.
  4. Run: outcome is ran, error (the exception text goes to last_result), missing-action (nothing registered under that action name: its module is off or never registered it), or skipped/held/postponed. One-offs are deleted unless the handler rescheduled the same key.
  5. on_result = App._job_done, which emits job_failed for error (the exception) and missing-action (no action '<name>').

Handlers run on the event loop thread. A slow synchronous handler (git, a zip, an HTTP call) blocks every other job and async task for its duration; long work should start a thread (threading.Thread, asyncio.to_thread) as gbrain, books, retro, profile and handwritten do.

Keys are "<module id>:<name>" so Module.stop() (cancel_prefix(f"{id}:")) removes them; actions are "<module id>.<name>". Module.every() and Module.action() build both. LABELS and describe() give the words /status and kurooto top show.

Jobs

core/jobs.py:Jobs, SQLite <state>/jobs.db. The only way a feature should run a full AI request.

jid = app.jobs.submit(
    prompt,
    title=None,
    effort="auto",  # "low" | "medium" | "high" | "auto"
    reply_to=None,
    quiet=False,  # quiet: no answer is sent (the then-action handles it)
    then=None,
    then_payload=None,  # a follow-up registered in app.jobs.then_actions
    background=False,
    text_only=False,  # background: waits for the charger and for kept free limits
    why=None,  # a Calm reason for an answer that comes by itself
    lane=None,
    brain=None,  # lane "you" | "bg" | "chk"; pin to a brain id
)
  • Status: queued → running → ok | failed. Verdicts are providers.base.Verdict.
  • Lanes (LANES = ("you", "bg", "chk")): one job at a time per lane, so the user's own request never waits behind background work. Unset, background=True goes to bg, everything else to you. chk is a second background lane so two agent programs can work at once (the concept graph's check role, call reviews).
  • Worker (Jobs.worker, an asyncio task): recover() first (jobs left running by a dead process, identified by runner = pid plus start time, go back to queued), then every 5 s or on poke(): watchdog(), and for each free lane _claim() the oldest ready job and run it in a thread (_start). Nothing runs while paused; background jobs only run in normal power mode (_READY).
  • Effort: a fixed low/medium/high, or providers/effort.py:pick (see brains.md). Timeout per level: brain.timeout_min.
  • Retries are the fallback chain, not repeats: each brain in [main, fallback, last resort] (rearranged by Quota.arrange) is tried once; RETRY verdicts move on. There's no automatic re-run of a failed job; features that need one (the concept graph) count tries themselves.
  • Deferral: background work whose free limits are kept for the user goes back to queued with not_before (_defer, event job_deferred); resume() clears it when a limit answers again.
  • Watchdog (watchdog()): a running job of this process with no AI process and no sign of life (_mark updates activity) for jobs.stuck_min minutes ends stuck; one past its deadline (time limit plus the brain's grace_s plus GRACE_S = 120) ends timeout. Ending kills the process tree (proc.kill_tree).
  • Cancel: cancel(jid), cancel_text("all"), /jobs, POST /api/jobs/cancel, kurooto jobs --cancel.
  • Delivery (_deliver, unless quiet): [<brain label> · <effort>] <title> then the answer, through app.notify(kind="result", why=job.why or "asked", reply_to=...). Answers over LONG = 7000 chars are also sent as a file (jobs/<id>-result.md). Cases adds a Wrong button when on.
  • Run receipt (0.5.15): _run builds one line from the run's own record before the request's tool log is dropped (Jobs._receipt → receipt()), and keeps it in the receipt column: the AI (NAMES), effort, time since it started (fallback tries included), the share of today's limit when Quota.status(pool)["pct"] knows the limit, and what it did from Jobs.steps (_did: each tool in ACTS becomes a phrase like "wrote 2 notes", the rest "used N other tools"; none is "did nothing", or "did nothing through Kurooto" for an agent program, whose own tools Kurooto doesn't see). At most RECEIPT_MAX = 120 characters. Jobs.receipt(jid) gives it while jobs.receipt is on: _deliver adds it as the message's last line and passes it as Message.tail, which the Telegram sender (TelegramAPI.send(tail=)) marks italic with a message entity (UTF-16 offsets, no parse mode, so the answer needs no escaping); other channels show it as plain text. GET /api/job (web/tools_api.py:job) appends it to answer and returns it as receipt, so the terminal chat, kurooto ask and the dashboard show it too. Quiet requests are never delivered, so they get none. Tests run with it off (tests/conftest.py:no_receipts); tests/unit/test_receipt.py turns it on.
  • Chat history (0.5.8): after delivery, the answer is recorded into Chat's history only if chat.owns(job.id) (modules/chat.py:Chat.owns, the set of job ids Chat.ask submitted). Digests, research, call reviews and skills therefore never become "the conversation".
  • Tool log (0.5.8): Jobs.note_step(jid, name, args) records each tool use of a request running in this process in Jobs.steps[jid] (at most MAX_STEPS). API brains reach it through Task.run_tool (run_tool(..., job=jid)); agent programs through kurooto mcp, which sends the request's id from the KUROOTO_JOB variable (core/mcp.py:ENV_JOB, put into Task.mcp_env by _run) as job in POST /api/tools/call. When a brain's Result.usage has no tool_calls, the log's count is used, so attempts.tool_calls and /usage count agy and Claude Code too. The log is dropped when the request ends.
  • Watchers (0.5.8): app.jobs.watchers holds fn(job, result, info) called by _after for every finished request, after delivery and the then-action, success or not, with info = {"steps", "then", "payload"}; a failure emits job_watcher_failed. Learns from its own work (modules/learning.py) is the one user. finished_since(t) lists requests that ended well after t (its search index).
  • Then-actions: app.jobs.then_actions[name] = fn(job, result, payload), run by _after after delivery, for success and failure alike (check result.ok). A name not registered when the job finishes is skipped silently, so register then-actions in __init__ or start(), never lazily just before submitting (modules/google.py registers google.draft lazily and loses drafts across a restart). Exceptions become job_then_failed. result.usage["limits"] lists every usage limit hit on the way ({"brain", "retry_after_s", "detail"}), also one a stand-in then answered for; the concept graph's reading budget reads it (core/readbudget.py).
  • Shutdown: halt() stops running jobs where they are; they stay running and recover() re-queues them at the next start.
  • usage(days) (from attempts) feeds /usage; public(job) is what the dashboard and CLI may show (no prompt, no answer).

Events

core/events.py: Events(state).emit(kind, **fields) -> dict appends {"ts": iso, "kind": kind, ...} to <state>/events.jsonl (a field named kind is stored as subkind), then calls every subscribe(cb) listener in this process. tail(n, kinds=None) reads backwards from the end a block at a time (lines_back, Events.lines()), so its cost is what it reads, not the log's size. Writes are serialised by a thread lock only; CLI processes append to the same file but their events never reach the daemon's listeners. Like the logs it's trimmed: past MAX_BYTES (10 MB) emit moves it to events.jsonl.1 (replacing the one before) and starts a new one; tail, Events.lines() and health.Latest read on into .1. Notify and Calm

core/notify.py:Notifier; app.notify(text, **kw) is the one way to tell the user something.

  • Message fields: text, title, buttons ([[("label", "prefix:ref:action" | {"url": ...}), ...]]), kind (info | result | reminder | question | approval | deadline | call | update), urgent, reply_to, map_kind / map_ref (so a reply or button finds its handler: Module.replies()[map_kind]), file, tail (the text's own last line to show quietly: the run receipt, italic on Telegram), and the Calm envelope why, setting, about, item, due.
  • send(): Calm decides first (Calm.decide: send, hold or stop); during focus, non-urgent messages that aren't approval/call go to focus-queue.jsonl (flushed by flush_queue() when focus ends); otherwise _deliver(): Telegram (unless presence holds it because the network is down), the phone app for notify.app_kinds, the desktop (core/desktop.py) for notify.desktop_kinds or when no other channel delivered. Emits notified.
  • Channels are registered by modules: notifier.register("telegram", send, retract=None). retract(map_kind, map_ref, button) takes a question down from channels that keep copies (the phone app) once it's dealt with anywhere.
  • Button data is "<prefix>:<ref>:<action>"; App.callback routes core prefixes (calm, upd, ask, health, fixme, job, inf, ton, keep, fgt, rhy) and then each enabled module's callbacks()[prefix]. Keep a module's prefixes unique and short (Telegram limits callback data to 64 bytes).

core/calm.py:Calm:

  • Every message that comes by itself carries why=<reason id>. Reasons are declared in REASONS (built with R(id, what, setting=..., stop=..., fewer=..., later=..., exempt=..., suggest=..., feature=...)). A message with why="asked" (ASKED) is an answer to the user and is never held, counted or buttoned; a message with no why is sent and recorded as "No reason recorded".
  • Exempt (EXEMPT): own (reminders the user set), alarm, approval, deadline (due within DEADLINE_H = 12), urgent, security, bundle.
  • The daily limit: notify.calm.messages (6) and notify.calm.calls (1, Calm.call_ok). Past it, messages are held for the evening bundle at notify.calm.evening_at (20:00, sent by calm:tick). Per-kind user choices: stopped, evening, fewer. Exam season tightens it (modules/exam_season.py:budget_during_exams). Calm.day_limit() is the messages limit after Rhythm.lighter_limit (half on a lighter day); _wait holds with "quiet" during a quiet week (Rhythm.quiet_week), like "exams", past the evening too. Two per-kind rules Dreaming tunes (core/policy.py): habituate (kind → N: Calm.ignored(why, t), the streak() of answerable records left unanswered, at least IGNORED_H = 3 hours old, reaching N holds it as held="habit") and windows (kind → "HH:MM-HH:MM", inside(); outside it held="window"). Both are checked in Calm._wait after fewer.
  • On Telegram a counted message gets "Why?" and "Less of this" (calm:<rid>:why|less); Less of this offers Stop / Fewer / Another time, each changing one setting (Change), with Undo. /calm and /why show the state.
  • Records: calm.db table sent (45 days; Calm.forget blanks text and title after privacy.keep_days). notify.calm.on = false turns all of it off.

To add a message that comes by itself: pick a reason id <module>.<what>, add an R(...) to REASONS with the setting that controls it (so Less of this can change it), and pass why= (plus about=/item= when it concerns one thing) to app.notify. A message without a reason still works but can't be turned down.

Quota (free AI limits)

Egress: every request on the internet

core/egress.py. New code never calls urllib.request.urlopen (or another HTTP client) for an internet address; it calls egress.urlopen(req, "<feature>", timeout=..., own=...), which takes the same Request or URL, returns the same answer (wrapped to count the bytes read; use it as a context manager) and raises the same errors.

  • _check: 127.0.0.1, localhost, ::1 pass without a count (nothing leaves); privacy.egress off passes everything. Otherwise the host is on the list when it's in HOSTS (exact, or .domain for every host under it) or in privacy.allow_hosts, or the call site says own=True: an address the user gave (the iCal link, a Research feed, the custom AI service's base_url, the call line and its ntfy server, the AI's fetch tool, whose pages are chosen for the user's request). In enforce, a host that's none of those raises Blocked, an urllib.error.URLError whose text names the host and privacy.allow_hosts, so existing except OSError / URLError handling copes. record (the default) counts it with unlisted.
  • urlopen counts len(req.data) out and what's read in, once, when the answer is closed (_Counted); a request that raised (an HTTPError too) is counted with what went out. urllib.request.urlopen is looked up at call time, so tests that put a fake there still work. Redirects are followed by urllib and aren't checked again.
  • allow(url, feature, own): the same check for a connection made another way (calls/connector.py's websocket), counted once per connection, no bytes.
  • handed(program, feature): a subprocess that goes online by itself, counted as "handed to <program>" and not looked into: providers/agy.py:Agy.run, providers/claude.py:ClaudeCode.run, git's GIT_ONLINE steps in modules/notes_sync.py:NotesSync.git (not for a local remote) and core/profile.py, calls/deploy.py (_wrangler, npm ci), local_models.py (a pull through Ollama), gbrain.py:GBrain.run (ONLINE steps when the index uses Gemini or the brain is the user's own), skills.py (Tectonic), core/prereqs.py:Prereqs.install (HANDED kinds).
  • The ledger: <state>/egress.json, {"days": {"YYYY-MM-DD": {"<host>|<feature>" or ">program|<feature>": {host, via, feature, n, out, in, blocked, unlisted}}}}, the last DAYS (30) days, at most MAX_ROWS rows a day (then other). record takes a thread lock and the egress file lock (2 s; on timeout the count is dropped) and never raises. attach(app) (in App.__init__) points it at the running app's state folder and settings; before that (a bare CLI command, the launcher) nothing is counted and only HOSTS applies.
  • /egress is a core command (App.handle → command): week() sums the last SHOWN (7) days per row, blocked first, then by count.
  • HOSTS and docs/PRIVACY.md's "Where requests go" table must list the same hosts (tests/unit/test_egress.py:test_the_privacy_page_lists_the_same_hosts). A new built-in host goes into both, with the feature that reaches it.
  • Not routed, on purpose: requests to this computer (top.py, cli.py, core/mcp.py, core/rerank.py, modules/local_models.py:LocalModels.api, modules/google_confidential.py: Ollama and Kurooto's own page). Add-ons' own code is counted only when it uses egress.urlopen.

Running programs

  • core/proc.py:run(args, *, input=None, timeout=60, cwd=None, env=None, on_start=None) -> Result(code, out, err): long text goes through stdin, npm .cmd shims run through node directly (resolve_cmd_shim), UTF-8 decoding, no console window on Windows (CREATE_NO_WINDOW), a new session on POSIX, and the whole process tree killed on timeout (kill_tree). which(name, extra_dirs) also looks in user install folders; ensure_user_path() adds ~/.local/bin, ~/.cargo/bin and Homebrew to a short boot-time PATH. Windows notes

  • Paths: %LOCALAPPDATA%\Kurooto (not Roaming); the program in %LOCALAPPDATA%\Programs\Kurooto. Documents and Downloads come from SHGetKnownFolderPath (OneDrive may have moved them; core/places.py:_known_folder).
  • Renames fail transiently while a scanner holds a file: always go through jsave / write_note_file.
  • Always pass encoding="utf-8" to text I/O; the default is a code page.
  • No console windows: CREATE_NO_WINDOW for helpers (core/proc.py, daemon.supervise), DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP for programs that outlive the call (cli.py:start_background, core/opener.py). pythonw.exe has no stdio: core/mcp.py:_console and modules/terminal/plan.py switch to python.exe.
  • Command lines are limited to about 32 000 characters and cmd.exe mangles " & ^ %: prompts go through stdin or a file (providers/agy.py:handover, ARG_LIMIT; Claude Code's context file).
  • npm programs are .cmd shims: proc.resolve_cmd_shim.
  • PTYs: ConPTY through pywinpty (providers/agy.py:run_pty, modules/terminals.py:WinPty), ptyprocess elsewhere.
  • No signals: loop.add_signal_handler isn't available, so Ctrl+C arrives as KeyboardInterrupt (daemon.run); sign-out and shutdown come through core/endsession.py.
  • File modes don't apply (jsave skips chmod on nt); secrets rely on the profile's ACLs or the Credential Manager.
  • The registry is used for autostart (core/autostart.py), PATH (core/pathfix.py) and the uninstall entry (cli.py:install_finish).

Turn on from chat (core/turnon.py)

At the end of App.handle's instant requests, turnon.offer(app, msg, plain, mods, asks) asks every module that's off for an intent whose match takes the text (errors are skipped, turnon_skipped). Not ready (Module.ready()): says where to set it up. Otherwise the text waits in <state>/turnon.json (20, for 24 h) under a ref, and the reply carries ton:<ref>:on / ton:<ref>:no (routed by App.callback). on enables the module's requires, then the module, re-matches and runs the intent with an Incoming whose replies go out through app.notify(..., why="asked"); no hands it to Chat when that's on. Only for msg.via in BUTTONS (telegram, app): the setup page's try-it box and terminals go on to the AI. Events turnon_offered, turnon_done. Setting turnon.offer. Tests: tests/unit/test_turnon.py.

Setting up from what's said (core/infer.py)

infer.observe(app, text, via) runs on every plain chat message (App.handle, before routing; it never consumes the message) and every daily.append body. Rules only: PROJECT + WITH (first person, no NOT words) start a project via modules/research.py:ensure_project and write With: <who> (<role>) and ## Meetings; MEET with a project person's surname logs a dated line (and sets Last met: <date>, LAST_MET, under the last With: line; undo puts back the one before), or a deadline "Meeting: <who>" when modules/text.py:when_from finds a time more than 30 minutes ahead; CLASS adds a subjects.timetable row for a known subject; REGULAR ("every <days> at <time> I go to/have/work <what>", or the other order; not for class, test or quiz words, which NOT_REGULAR leaves to the classes rule and Deadlines) adds a commitments.items row via modules/commitments.py:Commitments.add, turning the feature on if it was off (undo turns it off again when the list is empty); ALIAS ("by X I mean <subject>", "X is short for/stands for <subject>", "I call <subject> X") adds a short name to a subjects.list entry (one is made for a subject that's only in the term note or a class pack), refused for NOT_ALIAS words and for any name a subject already has. Each sentence is keyed (_key, sha256 of the normalised text) and looked at once. Changes are kept in <state>/inferred.json (items with their undo data, seen); undo() reverses one (a note it made and nobody touched is deleted; otherwise only its own line goes); App.callback routes inf:<id>:undo, /inferred is in App.handle and CORE_HELP. Calm reason infer.done. Settings infer.on, projects, meetings, classes, aliases, commitments. Tests: tests/unit/test_infer.py.

Keep or drop (core/keep.py)

app.keep (Keep) counts what the user uses of each feature: Keep.used(module, how, via) with how one of intent, command, button, tool, reply. Called from App.handle (a module's replies() handler, its command, its intent; a taught or classifier-picked intent through intent_owner), App.callback (a module's button), modules/calls/__init__.py:Calls.run_tool and core/tools.py:run_tool with via="call" (tool_owner: the module whose call_tools() has it, else calls). via="setup" (the try-it box) isn't counted. Stored in <state>/keep.json: used[module][YYYY-MM-DD][how] (pruned to KEEP_DAYS = 90 by the tick), last[module], since (set by the first start()), first, monthly_at, answered[module].

keep:tick (daily 12:00): with setup.done, at FIRST_DAYS = 10 after since, one message (Calm reason keep.ask, kind question) lists every enabled feature but NEVER = ("telegram",) with counts(days) and Calm.sent_by(since) (messages and calls that came by themselves, not exempt own), and a row per feature (least used first, at most MAX_ROWS = 15): keep:<id>:keep|quiet|off (routed in App.callback). After UNUSED_DAYS = 60 of counting, at most every MONTH_DAYS = 30: idle() = enabled features with no use for 60 days, a recurring job under <id>:, and no answer in AGAIN_DAYS = 90. keep.ask = false sends neither (the day-10 one is then skipped for good).

Quiet is quiet_change(): a Calm Change adding the feature's non-exempt, stoppable REASONS to notify.calm.stopped (offered only while Calm is on and something is left to stop). Off is Change(module=id) (App.disable; not offered when another enabled feature requires it). Both go through Calm.apply, so Undo is calm:<uid>:undo. Calls a quiet feature places aren't stopped (Calm.call_ok doesn't read the stopped list). /keep (Keep.command, in App.handle and CORE_HELP): counts for 30 days, /keep <1-90>, /keep <feature> with its row. Events keep_asked, keep_answer, keep_failed. Tests: tests/unit/test_keep.py.

Your rhythm (core/rhythm.py)

app.rhythm (Rhythm), started after Keep; rhythm:tick every 30 min runs, outside the night, learn() once a day (looked in <state>/rhythm.json) and tell_lighter(), and absence() always (it checks the night itself). Errors go to rhythm_failed per part. Rules only, no AI.

  • Quiet hours. usual() reads ACTIVE events (message_in, button_tapped, call_answered, alarm_up_now) of LEARN_DAYS = 21, keeps per wake date the longest gap of QUIET_MIN_H–QUIET_MAX_H (4–16 h), skipping a gap that ends within BACK_MIN of Kurooto coming back online (Presence.offline), and with LEARN_NIGHTS = 7 or more takes the circular middle (middle()) of starts and ends, rounded to 30 min, within NIGHT_MIN_H–NIGHT_MAX_H and an end between WAKE_FROM and WAKE_TO (03:00–18:00). Stored as usual (the alarm's suggest() reads it via usual_hours()). learn() (availability.learn_night) moves availability.night.from/to when either end is LEARN_GAP_MIN (60) off, and with availability.learn_morning the MORNING settings (checkins.day_starts wake − 2 h, dreaming.when wake + 30 min, startby.when wake + 1 h, only single daily HH:MM specs); never a key the user set (_yours: a user value other than the last learned one). Cooldown AGAIN_DAYS (7), UNDONE_DAYS (30) after Undo. Changed modules are restarted (_restart: Module.start(), so every jobs take the new spec). One message, Calm reason rhythm.night, rhy:night:undo (restores each key it still holds, Settings.reset where there was no user value). Event rhythm_night_learned, rhythm_night_undone.
  • Lighter days. lighter(day) (notify.calm.lighter_after): the previous check-in day (from checkins.day_starts) had an exam deadline (open or done) due in it, or HEAVY_H (8) study hours on its date (Study.totals). Used by Calm.day_limit (lighter_limit), Checkins._plan (first check-in LATER_MIN later) and the morning line lighter_line(mark) (Dreaming's report when it's on, else tell_lighter(), Calm reason rhythm.lighter), once a day (lighter_told). rhy:lighter:no sets not_today and calls Checkins.unlighten. Events rhythm_lighter, rhythm_lighter_cancelled.
  • Absence. absence() (availability.absence_days, 2): last_seen() that many days back, Kurooto offline less than half of it, not night/focus/quiet/paused/quiet week, and not already asked for this seen: one question, Calm reason rhythm.absence, rhy:absence:fine|busy. Busy: Availability.set_quiet a week and quiet_until in state (quiet_week()); its reply (why="asked") has rhy:quiet:undo. Events rhythm_absence_asked, rhythm_quiet_week.

Tests: tests/unit/test_rhythm_learn.py.

The message policy: Dream RSI, part two (core/policy.py)

Dream-RSI (arXiv 2609.14858) mapped onto Calm: the base assistant isn't changed; a small policy decides when messages that come by themselves reach the user; every past message is the record; offline, the record is a replay simulator that can reorder (now vs. the evening bundle) but never invent outcomes; each night variants are proposed, today's policy is always one of them, all are scored on the whole record, and the best becomes the new policy only if it wins by a margin. Part one is Dreaming's self-check (modules/dreaming.py:self_check).

  • The policy (Candidate, today(app)): evening (notify.calm.evening), habituate (notify.calm.habituate), windows (notify.calm.windows). Everything else in Calm, availability and the user's settings is a hard constraint. Tunable kinds (tunable(why, never)): a known Reason, not exempt, later true, not in dreaming.never_tune. Kinds the user already has an entry for (in any of the three, stopped or fewer) or whose change from here was undone or reverted within BLOCK_DAYS = 30 (blocked()) aren't proposed.
  • The record (record(app)): calm.db rows with kind!='ring', a known why, state sent or bundled, no exempt (all 45 days: the pool grows to that), as Row(ts, why, bundled, held, answered, answerable); answerable = it had buttons or a reply mapping. calm_less events mark the latest row of that reason in the day before as less.
  • The replay (replay(app, c, rows, base)): per judged row (tunable, and answerable or less), Candidate.place(row, ignored, evening) says now or evening: after that day's evening_at always now; a row held for a reason the policy doesn't own (limit, fewer, exams) stays evening; then evening, windows, and habituate against streak() over earlier rows of the kind. Score: +ANSWERED (1) for an answered row still in time; -DELAYED (5), or -DELAYED_QUICK (10) when answered within QUICK_MIN = 30 minutes, for one sent now and answered before that evening that the policy would hold; -IGNORED (1) for an unanswered interruption, -IGNORED_BUNDLED (0.2) in the bundle; -LESS (2) for a less row sent now; minus CHANGE[lever] (habituate 0.5, window 0.75, evening 1.0) for a variant. With base, saved and delayed count rows that differ from it.
  • A round (tune(app), once a day: dream-policy.json day): propose() makes one-setting variants for the TOP_KINDS = 3 kinds with the most unanswered interruptions (at least MIN_SEEN = 5 judged, MIN_IGNORED = 3): habituate N in HABITUATE_N = (2, 3, 5), the evening bundle, and a window from the hours of the answered ones. The best strictly beats today's or today's stays (so it's never worse on the replay); it's applied only when it beats today's by dreaming.tune_margin (3.0), through Calm.apply(change, why=BY) ("dreaming.policy"), so Undo is calm:<uid>:undo. Every round is kept (last 30) and emits dreaming_policy; an exception emits dreaming_policy_failed and costs nothing else.
  • Dreaming's hook: Dreaming.report calls policy.morning(app, send): (lines, buttons); it tunes only for the sent morning message (/dream shows today's decision again) and gives one "Learned while you slept: ..." line with an Undo button. /dream policy is policy.show(app).
  • Adding a lever: a Calm setting _wait reads (the runtime, with a HELD text), its rule in Candidate.place (the replay must decide it from recorded fields only), its proposals in propose() with a CHANGE cost and a Candidate.said()/change() branch, KEYS, and a test in tests/unit/test_dream_policy.py. Never a lever that sends something that wasn't sent: the replay can't judge it.
