# What the AI knows about Kurooto (the self-manual)

Since 0.6.0 the AI that answers a request (and a user's own agent) can read what Kurooto is and what it's running, so
"why didn't it ring?" or "which model answered?" is answered from facts. Two parts, both read-only for the AI. The
user's view: [../user/ai-brains.md](../user/ai-brains.md#your-ai-knows-whats-running).

## The shipped manual: `src/kurooto/data/ai-manual.md`

How Kurooto works, in plain terms, for its AI: what it is, how a message becomes an answer (instant rules, the queue's
lanes, effort, the brain chain and fallback, the run receipt), what each request gets (context, tools, folders),
what the AI may and may not do (never reword the user's notes, never claim what it didn't do, the tap rules, egress,
Calm, no fixing by itself, no secrets), how to diagnose, and where things are.

- The part above the marker line (`tools/gen_ai_manual.py:MARKER`) is written by hand.
- Everything below it is generated by `tools/gen_ai_manual.py` from the code: every feature (`app.modules`: id,
  title, the first sentence of its description, its commands), Kurooto's own commands (`core/commands.py:CORE`,
  `SYNC`), the guarded actions (`core/tap.py:GUARDED`, `BY_ITSELF`) and the settings' sections with a fingerprint of
  every setting's name (from `tools/gen_settings_guide.py:collect`). It runs a scratch `App` under a temporary
  `KUROOTO_HOME`, so nothing of anyone's own is read.
- **It can't drift:** `python tools/gen_ai_manual.py --check` exits 1 when the generated part differs from the code.
  `tests/unit/test_brains_self.py:test_the_manual_is_current` runs it, `test_the_manual_names_every_feature_command_and_tap_rule`
  checks every module id, command and guarded action is in it, and `tools/release.py:build` calls `fresh_docs()`
  (this check and the settings guide's) before it builds anything. A release with a new feature, command, tap rule or
  setting therefore can't be built until the manual is regenerated: `uv run python tools/gen_ai_manual.py`.
- When you change how something works (not only add one), update the hand-written part too; the check can't see that.

## This computer's part: `<state>/reserve/self.md` (`core/selfdoc.py`)

`build(app)` writes Markdown sections: Kurooto (version, update channel and mode, when the daemon started, the
assistant's name), this computer (`platform`, the cached `hardware.json` machine or `hardware.detect`, the hardware
profile, the power mode), AI (`brain.main` and `brain.fallback` with `available()`, `has_worked()`, models per effort
and any limit wait from `providers/fallback.py`; the fallback order and `fallback_on`; `brain.classify` and the local
model; the concept graph's roles; today's quota counts), the last 8 requests (status, verdict, brain, model, effort,
seconds, lane: never titles or words), features (each one that's on with its health check from
`app.health.evaluate(net=False, save=False)`, and the ids that are off), the last 24 hours' failures, where things are,
and how to look further.

**Failures** (`failures(app)`): the event log read backwards (`core/events.py:lines_back`, both files) for a day:
`job_done` with `ok` false and any kind matching fail, crash, error, limit, stuck, timeout, retired or denied, counted
by kind plus the fields in `KEEP` whose values match `SAFE` (ids, verdicts, brain names). An `error` field is cut to
its exception class (`ValueError`), because error text can quote what was being worked on. Never message contents.

**When it's written:** `core/reserve.py:refresh` (at start and every 10 minutes) calls `refresh(app)`, which writes
it when `stale()`: the file is missing, `fingerprint(app)` changed (the version, `modules.enabled`, the `brain`
settings, `updates.channel`, `quota.on`) or it's older than `MAX_AGE_S` (600 s). The fingerprint and time are in
`reserve/.self.json`. Reading it through the tool or `for_request` refreshes it the same way, so a settings change is
seen by the next question. `kurooto reserve` writes it now.

**Who reads it:**
- the tool `kurooto_self` (`tool(app)`, added to `core/tools.py:agent_tools`, `writes=False`): `self.md`, or the
  manual with `part=manual`;
- `kurooto mcp`: resources `kurooto://self` and `kurooto://manual` (`core/mcp.py:RESOURCES`, `resource_text`), read
  from files so they answer while Kurooto is stopped (with the file's age when it's over 15 minutes old); Claude Code's
  per-run permissions allow `ListMcpResourcesTool` and `ReadMcpResourceTool`;
- agent programs directly: it's in the reserve folder, which `core/places.py:read_roots` already includes, beside a
  copy of the manual (`reserve/ai-manual.md`); `agent-guide.md` lists both;
- every request's context has one line pointing at it (`providers/context.py`); a request about Kurooto itself
  (`wanted(prompt, name)`: the assistant's name, "which model answered", "isn't working", "why didn't my alarm ...",
  "fallback", "usage limit", "fixme"...) gets the file in its context (`for_request`, at most `CONTEXT_MAX` 6000
  characters), through `core/jobs.py:Jobs._run`;
- `/fixme ai` (`core/fixme.py:explain`): the rules' answer plus `self.md`, text-only.

**Privacy:** nothing in it is a message, note, request title, answer or secret (no key or token is read here). It
leaves the computer only with a request about Kurooto itself, when the AI calls the tool, and with Ask my AI: see
docs/PRIVACY.md ("What Kurooto is running"). `tests/unit/test_brains_self.py:test_self_md_says_what_runs_without_contents_or_secrets`
checks a saved key and an error's words don't appear.

## Keeping it current in each release

1. Changed a feature, command, tap rule or setting? `uv run python tools/gen_ai_manual.py` (the test and
   `tools/release.py build` fail until you do).
2. Changed how something works (the queue, fallback, receipts, where files are)? Edit the hand-written part of
   `ai-manual.md` and, if `self.md` should show it, `core/selfdoc.py:build`.
3. A new file or state the AI should know about: add it to "Where things are" in both.
